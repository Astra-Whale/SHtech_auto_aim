## 前置知识

在进入任何算法细节之前，我们需要先理解几个最基础的数学和物理概念。如果你已经学过这些，可以把这一章当作快速复习。

### 坐标系的物理直觉

在自瞄系统里，你一共需要面对 **4 个坐标系**。

| 坐标系 | 原点固定位置 | X 轴 | Y 轴 | Z 轴 |
|--------|-------------|------|------|------|
| **图像坐标系** | 图像左上角 | 水平向右（u） | 垂直向下（v） | —（2D） |
| **相机坐标系** | 相机光心（镜头组内部） | 向右 | 向下 | 向前（光轴方向） |
| **云台坐标系** | 云台 yaw/pitch 旋转轴交点 | 向右 | 向前 | 向上 |
| **世界坐标系** | 云台旋转轴交点 | 指向 IMU 初始化时的 yaw=0 方向 | 水平面内的正 yaw 方向 | 铅垂向上 |

**注意！** 大部分队伍的自瞄都至少有这些坐标系，但它们的指向往往**不一样**，甚至不一定是**右手系**（比如上科大26自瞄的部分系）。使用之前一定要确认清楚，这里只是约定并作为演示。

你可能会问：*为什么云台坐标系和世界坐标系的原点一样？* 

因为2026年的绝大部分自瞄都不对自身运动状态做估计，所以它们将世界系的原点也固定到了云台旋转中心的那个物理点。世界系和云台系（枪口系）区别只在于——云台坐标系跟着云台一起转，世界坐标系的朝向是固定在空间中的。所以世界坐标系是一个"半世界系"：**朝向固定，原点随车**。

本文统一采用工具函数 `pw_to_yaw()` 的水平角约定：`yaw = atan2(y, x)`。因此，世界坐标系的 X 轴是 yaw=0 的参考方向，Y 轴决定水平面内的正 yaw 方向。几何位置仍写作 `(x, y, z)`，传给滤波器的 4D 观测则按 `[y, x, z, yaw]` 排列。

> **参见 ALGORITHM_GUIDE.md §3.7.2** 中 `R_world2imu` 的定义与计算方式。

### 刚体变换：两个坐标系之间怎么"翻译"

当你有一个点在坐标系 A 中的位置 `P_A`，想知道它在坐标系 B 中的位置 `P_B` 时，需要做一次 **刚体变换**（rigid transform）。刚体变换包含两步：

```
P_B = R_A2B × P_A + T_A2B

其中：
  R_A2B  — 旋转矩阵 (3×3)，描述 A 系需要"扭"多少才能对上 B 系的方向
  T_A2B  — 平移向量 (3×1)，描述 A 系原点在 B 系中的位置
```

**直觉**：先把 A 系中的点按 `R` 扭到与 B 系同方向，再把原点偏移 `T`。

旋转矩阵 `R` 的一个性质：**它是正交矩阵**，也就是说 `R^{-1} = R^T`。当你需要反向变换（从 B 到 A）时，直接用转置就行：`P_A = R_A2B^T × (P_B - T_A2B)`。

而旋转矩阵本身是怎么来的？最常见的方式是用 **欧拉角（yaw, pitch, roll）** 来描述。在 RoboMaster 自瞄系统中，这三个角来自云台 IMU，分别表示绕 Z 轴、X 轴、Y 轴的旋转。

> **注意**：欧拉角的旋转顺序会影响最终得到的旋转矩阵。本系统的约定见 ALGORITHM_GUIDE.md §2.3。

### 相机成像模型：从 3D 世界到 2D 图像

相机本质上是一个 **3D → 2D 的投影器**。最常用的模型是 **小孔成像**（pinhole model）：

```
一个 3D 点 P_cam = [X, Y, Z]^T （在相机坐标系下）
投射到图像上的像素坐标 [u, v]：

    u = fx * (X / Z) + cx
    v = fy * (Y / Z) + cy

其中：
  fx, fy  — 焦距（以像素为单位）
  cx, cy  — 主点（光轴在图像上的落点，通常接近图像中心）
  X/Z     — 归一化坐标：Z 越大，点越靠近图像中心（透视效果）
```

这 4 个数 `(fx, fy, cx, cy)` 和径向畸变系数 `(k1, k2, p1, p2, k3)` 共同构成了相机的 **内参**（intrinsic parameters）。标定内参的过程，就是确定这些数的过程。

**为什么理解这个很重要？** 因为本文的核心动作——从 2D 图像角点反推出 3D 装甲板位置——就是上述过程的反向操作：PnP（Perspective-n-Point）。你把 4 个已知 3D 点的相对位置（装甲板模型点）和它们在图像上的投影（神经网络检出的角点）喂给 `solvePnP`，它就能算出装甲板在相机系下的 3D 位置。

### 卡尔曼滤波的直觉

在自瞄系统中，你每一帧都能测得目标装甲板的 3D 位置 `(x, y, z)`。但你有两个问题：

1. **测量值有噪声**：神经网络的角点、IMU 的数据都不是完美的，你拿到的 `(x, y, z)` 会在真实值附近抖动。
2. **你还需要速度**：仅仅知道位置不够——你需要知道目标往哪运动、有多快，才能预测它下一步会出现在哪里。

卡尔曼滤波就是同时解决这两个问题的数学工具。它的核心思想只有一句话：

> **"我不完全相信测量值，也不完全相信预测值——我根据各自的噪声大小，在两者之间取一个加权平均。"**

你可以用更直觉的方式理解：假设你有两个传感器在测同一个温度，一个精度 ±1°C，另一个精度 ±5°C。当你拿到两个读数时，你会更相信第一个传感器的读数，但也不会完全忽略第二个——卡尔曼滤波做的，就是精确算出这个"加权比例"。

在自瞄系统中，卡尔曼滤波用于从观测到的 3D 位置序列中，估计目标的真实位置和速度。几何位置使用 `(x, y, z)` 表示，PnP 结果组装为 `[y, x, z, yaw]` 后进入滤波器。滤波器输出平滑后的 `(x, vx, y, vy, z, vz, yaw, vyaw)`——每个维度都包含了**位置 + 速度**。

> **参见 ALGORITHM_GUIDE.md §3.7.3** 中装甲板模型 KF 的完整规范。

有了这些前置知识，你可以开始搭建自瞄系统了。

### 1.4 怎么解决

> **本场景涉及的核心技术**：传感器数据采集 · YOLO-Pose 目标检测 · solvePnP 位姿解算 · 坐标系变换链（图像→相机→云台→世界） · 6D→4D 位姿降维 · 线性卡尔曼滤波 · 云台目标角度解算

#### 模块1 — 传感器数据采集

**目的**：为每一帧处理准备好原始数据。

在这个阶段，我们获取所有我们在这一帧内需要的数据。向传感器抓取：
   1. 一帧图像
   2. 当前 IMU 姿态读数：云台的 yaw，pitch，roll
   3. 当前精确时间

> **为什么**：之后模块 2 用图像做检测，模块 3 用 IMU 姿态做坐标变换，时间戳则用于场景 2 之后的延迟补偿。这三个数据是整条算法链的燃料。

#### 模块2 — 装甲板探测

**目的**：从图像中找到所有装甲板，以及它们的角点、颜色、标号。

执行：调用在 RM 数据集上重新训练过的 YOLO-Pose 模型。像标准的 YOLO-Pose 那样——前处理、推理、后处理。对于场景 1，我们假设模型是完美的（C4），因此每个输出的角点都精确落在装甲板的四个顶点上。

> **为什么**：YOLO-Pose 是端到端的——它不仅告诉你"这里有装甲板"（bounding box），还直接输出 4 个关键点（灯条角点），这正是下一步 PnP 解算的输入。

#### 模块3 — 装甲板姿态解算

**目的**：通过装甲板的图像角点，解算出它在世界系里的位姿。

这是全系统最关键的几何链路。你需要让一个 2D 图像中的物体变成 3D 世界中的一个确定位置和朝向。分三步：

```
图像角点 (u, v)[4]
  │
  ├── Step 1: 2D → 3D（相机系）
  │   solvePnP(armor_3d_model_points, pts[4], K, distCoeffs)
  │   → rvec: 装甲板在相机系下的朝向（旋转向量）
  │   → tvec: 装甲板在相机系下的 3D 位置 [X_c, Y_c, Z_c]
  │
  ├── Step 2: 相机系 → 云台系
  │   P_imu = R_camera2imu × P_camera + T_camera2imu
  │   （R_camera2imu, T_camera2imu 来自外参标定，见场景 4）
  │
  └── Step 3: 云台系 → 世界系
      P_world = R_world2imu^T × P_imu
      （R_world2imu 来自当前帧的 Attitude，见前置知识）
```

**PnP（Perspective-n-Point）** 是 solvePnP 背后的算法。它的输入是：
- 4 个 3D 点（装甲板的物理尺寸——小装甲板 13.5cm × 5.6cm）
- 4 个对应的 2D 投影点（图像中检出的角点）
- 相机内参 K 和畸变系数

产出是在相机坐标系下的 3D 位置和朝向。

> **参见 ALGORITHM_GUIDE.md §3.7.2** 中装甲板 3D 模型点坐标的精确值。

装甲板的几何 6D 位姿包含 `(x, y, z, yaw, pitch, roll)`。但在这个理想场景下，目标步兵的装甲板 pitch≈15°（略向天空倾斜）且 roll≈0°（平行地面），这两个是已知常量。因此几何信息降为 4D `(x, y, z, yaw)`，再按当前代码的观测顺序 `[y, x, z, yaw]` 传递给下游。

> **为什么降维**：每多一个需要卡尔曼滤波跟踪的自由度，就多一个估计误差来源。如果你确定某些维度是常量（由机械结构决定），就把它们固定下来——这对滤波器的稳定性是免费的增益。

#### 模块4 — 卡尔曼滤波与目标状态估计

**目的**：从逐帧的 4D 观测值 `[y, x, z, yaw]` 中，平滑噪声并估计速度分量 `(vx, vy, vz, vyaw)`。

这是整个自瞄系统的核心滤波层。你拿到的每一帧 PnP 结果都是"此刻的观测"，但你需要的是"目标的状态"——包括它**此刻在哪**（位置）和**往哪走、走多快**（速度）。

**为什么需要速度？**

因为在弹丸速度有限（场景 7）或目标在运动时，做到"瞄准当前位置"是不够的——弹丸飞到目标位置需要时间，在这段时间里目标已经移动了。你需要预测"弹丸到达时目标会在哪里"。而预测的基础，就是知道目标当前的速度。

**线性卡尔曼滤波的基本形式**

在这个场景下，目标运动可以用最简单的匀速模型描述：

```
对于 X 轴（Y、Z、Yaw 轴同理）：
  状态: [x, vx]^T     （位置 x 和速度 vx）

  预测（无控制输入）：
    x  ←  x + vx * Δt  （位置按速度推进）
    vx ←  vx            （速度保持不变）

  更新（拿到测量值 z = x_measured）：
    x  ←  x + K * (z - x)    （用测量修正预测）
    vx ←  vx + (某个增益)     （速度也被间接修正）
```

其中的 **K（卡尔曼增益）** 决定了"你更相信预测还是更相信测量"。如果测量噪声大（PnP 解算抖动），K 会变小，滤波器更相信匀速运动的预测；如果测量很准，K 会变大，滤波器更服从测量值。

> **参见 ALGORITHM_GUIDE.md §3.7.3** 中装甲板模型 KF 的完整 4×2 维状态向量。

**两种跟踪模型的概念**

在整个自瞄系统中，根据目标的运动状态，你会有两种不同的跟踪策略。这里先建立概念——你现在用的是第一种，第二种将在场景 5 中引入。

| 模型 | 适用场景 | 跟踪的是什么 | 数学工具 |
|------|---------|------------|---------|
| **单装甲板模型** (Armor Model) | 目标低速运动或不旋转（< ~0.7 rad/s） | 装甲板这一块板子的 `(x,y,z,yaw)` + 各自速度 | 4 个独立的 1D 线性 KF |
| **整车模型** (Vehicle Model) | 目标高速自转（"小陀螺"，> ~0.7 rad/s） | 整辆车的旋转中心 + 旋转半径 + 转速 + 装甲板切换规律 | 1 个高维 EKF |

**在场景 1 中你只用单装甲板模型**。因为 C1 假设目标只是低速平移的 3 号步兵——它没有高速自转，装甲板不会来回切换，4 个独立 KF 完全够用。

为什么低速时不直接用整车模型？因为整车模型的 11 维状态中有一半是描述旋转的参数（旋转半径、转速、装甲板相位），在目标不转时这些参数没有观测量支撑，强行估计反而会发散。**原则是：目标不转就用简单模型，目标转起来才激活复杂模型**——这也是 ALGORITHM_GUIDE.md §3.7.3 中"双模型自适应跟踪"的核心思想。

在场景 1 中——目标只是低速平移的步兵——4D 匀速 KF 已经足够。当后面场景解除"单目标"或"感知误差"约束、目标开始高速旋转时（场景 5/8），整车模型就会登场。

#### 模块5 — 云台目标角度解算

**目的**：将**世界系**中的目标 3D 位置，转换为云台的两个旋转角（yaw 和 pitch）。

执行：从 KF 的输出拿到 `(x, y, z)` → 计算从云台原点指向该点的向量的方位角和俯仰角：

```
target_yaw  = atan2(y, x)       （水平面内的方位角）
target_pitch = atan2(z, √(x² + y²))  （垂直面内的俯仰角）
```


由于 C2 假设云台响应时间为零，这两个角度就是可直接下发给云台的指令。

> **注意**：本文采用 `atan2(y, x)`，与工具函数 `pw_to_yaw()` 一致。按本文约定，世界 X 轴是 yaw=0 的参考方向，世界 Y 轴决定水平面的正 yaw 方向。

> 我们刚才得到的是**世界坐标系**内云台应该指向的角度，称之为**绝对角**。2026年的rm视觉主流实践都对下位机发送绝对角。

### 1.5 现在我们能做什么

至此，在全部 C1-C6 理想约束下，你拥有了第一个能工作的自瞄系统。

**系统能力**：
- 能从相机图像中检出装甲板的 4 个角点（YOLO-Pose）
- 能通过 PnP + 坐标变换得到装甲板在世界系中的 3D 位置（模块3）
- 能通过卡尔曼滤波平滑位置噪声并估计速度（模块4）
- 能将 3D 位置转为云台瞄准角度（模块5）

**仍存在的局限**：
- 你的指令下发没有延迟补偿——一旦通讯有延迟（场景 2），云台就会"瞄错地方"
- 你的 IMU 和相机是理想同步的——真实传感器有噪声和时间差（场景 3）
- 你的相机没有运动模糊和光学约束——真实镜头的曝光、景深都会影响画面（场景 4）
- 你的 YOLO 角点是完美的——真实网络输出有偏差（场景 5）
- 你的算力是无限的——真实上位机需要流水线化（场景 6）
- 你的弹丸是瞬间到达的——真实弹丸有飞行时间和弹道下落（场景 7）
- 你的视野只有一个目标——赛场上同时有多台机器人（场景 9）
- 你的云台能瞬间响应——真实云台有惯性和摩擦力（场景 8）

**下一个目标**：场景 2 将打破"通讯零延迟"的假设。我们将第一次面对"你计算出的瞄准角发出去了，但云台在 T 毫秒后才收到"的现实问题。



## 场景2
### 2.1 我们从哪里来

在场景 1 结束时，你的自瞄系统能够：
- 从相机图像中检出装甲板角点 → PnP 解算世界坐标 → KF 滤波估计位姿和速度 → 计算云台瞄准角度
- **但所有这些都是在零通讯延迟的假设下工作的。**

你的指令——云台目标角度——是通过串口（典型为 UART）从上位机发送到下位机（单片机/云台驱动）的。在场景 1 中，我们假设发送和接收之间没有时间差。场景 2 要面对的是：**这个假设不成立。**

仍在生效的理想约束：
- ~~C5：理想通讯~~（本场景将解决）
- C1 单目标 / C2 理想执行机构 / C3 理想传感器 / C4 理想感知 / C6 无限算力

### 2.2 这次放松什么约束

- **放松约束 C5（通讯）**：现在，你的通讯总线和协议有延迟，并且会丢包。

这意味着：你在时刻 `t` 计算出的云台目标角度 `(target_yaw, target_pitch)`，下位机可能在时刻 `t + τ` 才收到。而在这 `τ` 毫秒内，目标可能已经移动了一段距离。如果你的指令不补偿这段位移，云台瞄准的将是"τ 毫秒前目标所在的位置"——而非当前位置。

### 2.3 新的任务是什么

> **在保证场景 1 全部功能的前提下，让系统能够感知、测量并补偿指令下发链路的延迟，使云台始终瞄准目标当前实际位置而非 τ 毫秒前的位置。**

具体来说：
1. **要知道延迟有多大**：不能凭感觉，必须有实测数据
2. **要评估是否需要补偿**：有些延迟足够小，可以忽略；有些不能
3. **要在算法中实现补偿**：用估算的未来位置替代当前位置发给云台

### 2.4 怎么解决

> **本场景涉及的核心技术**：通讯延迟测量 · 延迟补偿（指令下发链路）

#### Step 1: 测量——你的通讯到底有多慢？

在动手改算法之前，先搞清楚你的实际情况。

**方法 A：软件打时间戳（最常用）**

```
上位机：发送指令时记录 t1
下位机：收到指令时记录 t2
延迟 = (t2 - t1)  // 需要双端时钟同步，或测量来回耗时后除以 2
```

**方法 B：逻辑分析仪抓串口波形（最精确）**

```
逻辑分析仪挂在 TX/RX 线上 → 直接测量从字节发送完毕到应答返回的物理时间
```

你需要统计的不只是平均延迟，还有 **P99 延迟**（99% 的包在多少毫秒内到达）和 **丢包率**。因为最坏情况的延迟决定了你的补偿是否安全——如果 P99 延迟很大，你需要为最坏情况预留补偿余量。

> **经验法则**：笔者在 UART 921600bps、64字节包上录得平均 2ms 来回耗时，抖动和丢包率都极低。如果你的测量结果在此量级，可以直接进入 Step 2。如果高出很多，先检查串口配置和线缆质量。

#### Step 2: 判断——需要补偿吗？

延迟是否需要补偿，取决于它相对于目标运动速度的比例：

```
目标在 τ 内的位移 = v_target × τ

如果位移 << 关键尺寸，可以不补偿
如果位移与之相当或更大，必须补偿
```

对于典型的 RoboMaster 目标（步兵速度 ~3m/s），5ms 延迟意味着约 15mm 的位移。**保守策略是：只要延迟可测量，就补偿。**

#### Step 3: 补偿——怎么让指令"提前"发送

补偿的核心思想是：不要发"当前瞄准角"，而是发"预测的瞄准角"。

```
当前时刻 t 的目标状态（来自场景 1 的 KF 输出）：
  pos_world = (x, y, z)
  vel_world = (vx, vy, vz)

预测 τ 毫秒后的位置：
  pos_pred = pos_world + vel_world × τ

基于预测位置计算瞄准角：
  target_yaw  = atan2(pos_pred.y, pos_pred.x)
  target_pitch = atan2(pos_pred.z, √(pos_pred.x² + pos_pred.y²))

下发 (target_yaw, target_pitch) —— 这就是补偿后的指令
```

这里用到的 `vel_world` 正是场景 1 中 KF 估计的速度——这也解释了为什么模块 4 的 KF 需要同时估计位置和速度：**速度不仅用于目标跟踪，也直接用于通讯延迟补偿。**

> **参见 ALGORITHM_GUIDE.md §3.7.3** 中 KF 速度分量的估计公式。

**关于丢包**：如果丢包率很低（< 1%），最简单的方法是下位机保持最后一帧收到的有效指令不变，直到收到下一帧。如果丢包率较高，需要引入指令包序列号和重传机制，但这通常超出了视觉组的范围——应该让电控同学解决串口稳定性问题。

**延迟链的基本概念**

在场景 2 中，你只补偿了 `comm_latency`（通讯延迟）。但在最终系统中，Planner 进行目标未来位置预测时使用的总延迟窗口由四项组成——这是你在后续场景中会逐步建立的概念：

```
total_delay = process_latency + comm_latency + fly_time

  process_latency : 从图像采集瞬间到"此刻"的耗时
                    = now() - 图像采集时刻的时间戳
                    → 对应 ALGORITHM_GUIDE.md §3.8.6 中的 Planner 流程

  send_latency    : 指令从上位机发出 → 串口传输 → 下位机接收 的耗时
                    → 这是场景 2 你处理的部分

  comm_latency    : 超参，概括各种杂项延迟，比如电控从解包完成到电机运动（或者云台对位置指令跟随的滞后）
                    → 实际场景里你要手调这个参

  fly_time        : 弹丸从枪口飞到目标位置的耗时
                    = distance / bullet_speed
                    → 场景 7 中当弹速不再无限时引入
```

**四个延迟项的分工**：

| 延迟项 | 本场景 | 含义 | 后续哪个场景处理 |
|--------|--------|------|-----------------|
| `process_latency` | 暂不涉及（C6 无限算力 + C3 零采集时间） | 相机采集 + 图像前处理 + 推理 + 跟踪 + 规划的总计算耗时 | 场景 3（采集） + 场景 6（算力） |
| `send_latency` | **本场景处理** | 串口从 TX 到 RX 的物理传输 + 下位机解包 | — |
| `comm_latency` | 暂不涉及（实车才用） | 兜底超参，补偿各种误差 | — |
| `fly_time` | 暂不涉及（C2 弹速无限 → fly_time = 0） | 弹丸飞行中的目标位移补偿 | 场景 7（弹速限制） |

**关键理解**：你今天在场景 2 学的"用 KF 速度 × 延迟时间 = 预测补偿"，在未来的场景 6 和 7 中会完全复用——只是把 `τ` 从单纯的 `send_latency` 替换为 `total_delay = process_latency + send_latency + comm_latency + fly_time`。补偿的数学形式一模一样，变的只是"往前预测多远"。

> **代码参考**：`total_delay = process_latency + comm_latency + fly_time` 是 Planner 实际执行预测时的完整公式（参见 `planner/Planner.cpp#L371`），其中 `process_latency = now() - 图像采集时间戳`。实际代码里没有单独补偿通信延迟，将send项归入了comm项一并补偿。

### 2.5 现在我们能做什么

**系统新增能力**：
- 能够测量并记录通讯链路的延迟和丢包率
- 能够在指令下发时基于 KF 的 `vel_world` 预测 τ 毫秒后的目标位置
- 下位机收到的指令不再对应"瞄准当时那个瞬间的目标"，而是对应"瞄准指令到达时刻的目标预测位置"

**仍存在的局限**：

- 你的相机画面仍然是完美的——真实镜头会模糊（场景 4）
- 你的 KF 使用的观测值仍然来自"完美的 YOLO 角点 + 完美的 PnP"（场景 5）

**实践练习**：
1. 实测你的串口延迟（尝试方法 A），记录平均值和 P99
2. 根据你的目标典型速度（找电控同学要数据），估算 5ms vs 20ms 延迟下的位置误差
3. 在你的 KF 输出中，确认 `vel_world` 的量级和方向是否合理（如果目标在远处向你走来，vy 应该 > 0 且量级合理）

### 3.1 我们从哪里来

在场景 2 结束时，你的自瞄系统能够：

但所有这些能力都建立在一个脆弱的基础上：**你认为你的传感器数据是完美且同步的。** 你的代码里，图像拿到手就是"此刻"的画面，IMU 的 yaw/pitch/roll 就是"此刻"的姿态——它们之间不需要对齐，因为 C3 假设它们零延迟、零噪声且瞬间采集。

- ~~C5：理想通讯~~（已在场景 2 解决）
- C3：理想传感器（**本场景将解决**）
- C4：理想感知 / C6：无限算力 / C2：理想执行机构 / C1：单目标

### 3.2 这次放松什么约束

- **放松约束 C3（传感器物理约束）**：

在真实世界中，你面对的是：

1. **相机不以你的意志为转移**：它要么按固定帧率（如 200fps）自由运行，要么等你的触发信号——但无论哪种，曝光需要时间（μs 级），读出需要时间（ms 级），图像从相机传输到上位机内存需要时间（ms 级）。你一帧从物理世界的光线到上位机里的 `cv::Mat`，中间过了好几道物理关卡。

2. **IMU 不完美**：它有零点漂移（静止时读数不为零），有随机噪声（读数在真值附近抖动），而且 IMU 数据从单片机采样、打包、串口传输到上位机也需要时间。

3. **三个信息源互相异步**：相机帧有自己的时间线、IMU 有自己的采样周期、机器人状态（RobotStatus）通过串口不定时到达——它们之间没有任何天然的同步机制。你没办法说"第 100 帧图像对应的 IMU 读数就是此刻串口缓冲区里那包"——因为它们到达的时间不一样。

### 3.3 新的任务是什么

> **在真实传感器约束下，建立一套多源异步数据的时间对齐体系，使每一帧算法处理时拿到的图像、IMU 姿态和机器人状态都对应同一时刻（或同一时刻的最优估计），并将相机采集延迟纳入 `total_delay` 延迟链。**

具体来说：
1. **相机侧**：确定采集模式，在图像到达上位机的瞬间打时间戳
2. **IMU 侧**：理解 IMU 噪声/零飘的归属，评估 IMU 传输延迟是否需要补偿
3. **对齐侧**：设计以相机帧为主时钟的多源时间对齐策略
4. **延迟链侧**：让 `process_latency`（采集耗时）参与总延迟计算，为后续场景 6 做好铺垫

### 3.4 怎么解决

> **本场景涉及的核心技术**：相机采集模式（主动回调 vs 轮询缓冲区） · 拜尔模式原始数据传输 · IMU 互补滤波 · 时间戳对齐 · 多传感器异步融合 · IMU 四元数线性插值（Slerp） · 延迟链之 process_latency

#### 3.4.1 相机采集：拿到图像的第一时间，记住"它来自哪个瞬间"

工业相机有两种基本的采集触发模式：

**方式 A：相机主动回调（Event-driven）**

相机内部定时曝光 → 图像就绪 → 相机 SDK 调用你注册的回调函数 → 你在回调里拿到 `cv::Mat`。这种方式省 CPU，但你的代码被相机 SDK 的线程牵着走，不利于和你的主循环协同。

**方式 B：上位机轮询缓冲区（Polling）**

相机内部定时曝光 → 图像就绪 → SDK 把图像塞进一个内部环形缓冲区 → 你的主循环定时调用 `camera.grab()` 从缓冲区取最新一帧。**这是 RM 视觉的主流选择**，因为它让你在"你自己的时机"处理图像，而不是被相机的节奏打断。

> **经验法则**：主流 RM 视觉实现采用方式 B（轮询缓冲区）。你需要确保配置合理的缓冲区尺寸——太小会丢帧，太大会引入不必要的延迟。一般设 2-4 帧的缓冲区（即缓冲区深度 × 帧间隔 ≈ 总延迟上限）。

**最关键的一步：在图像到达上位机内存的瞬间打时间戳**

无论采用哪种方式，当 `cv::Mat` 对象从 SDK 传递到你手上的那一瞬间，立即记录：

```cpp
// 对应 ALGORITHM_GUIDE.md §3.3 Sensor 阶段
auto frame = camera->getFrame();
data->time = std::chrono::high_resolution_clock::now();  // 这就是"图像到达时刻"
```

这个时间戳是后续一切时间对齐和延迟计算的基础。`process_latency = now() - data->time` 的含义就是从图像到达上位机到"此刻你正在做 Planner 预测"之间的累积耗时。

**传输格式的选择**：

许多工业相机支持输出**原始拜尔模式数据（Bayer BG8/RG8）**而不是已插值的 RGB/BGR。拿原始 Bayer 有两个好处：
- 传输数据量小（单通道 8-bit vs 三通道 24-bit），降低传输时间
- 你可以在拿到图像的瞬间记录时间戳，然后在 CPU/GPU 上解拜尔（demosaicing）——在上位机上解拜尔的速度通常不是瓶颈

> **参见 ALGORITHM_GUIDE.md §2.2** 中图像格式规范（BGR `CV_8UC3`），这里的 BGR 是解拜尔之后的最终格式。

**曝光、读出、传输时间**：这三段构成了相机采集的物理延迟。在帧率 ≤ 300fps 的 RM 典型场景下，用软件打时间戳的方式足以近似（error < 1ms）。详细的硬件级时间测量可以暂不做——先保证你的延迟链里有一个准确的 `data->time`。

#### 3.4.2 IMU 数据的处理：分清楚你和电控同学的边界

**IMU 噪声和零飘**：这不是你的工作。

IMU 从芯片级就是一个有噪声、有零飘的传感器。消除噪声和零飘需要嵌入式侧的滤波——互补滤波、卡尔曼滤波、恒温校准——这些是电控组（嵌入式传感器组）的工作。你需要做的是信任他们给到上位机的 `Attitude` 数据是经过滤波的可用姿态。

> **🟡 交叉协作提醒**：和电控同学确认你的 IMU 数据链路——IMU 芯片 → SPI/I2C → 单片机 → 互补滤波 → 串口 → 上位机。确保他们知道姿态数据的传输频率（典型为 200-1000Hz），以及单片机端滤波的截止频率（不要过低，否则快速转动时姿态会滞后）。

**IMU 传输延迟**：这是你需要考虑但不一定要补偿的。

IMU 数据从单片机采样时刻到上位机收到的时刻，中间经历：单片机打包 → 串口发送 → 上位机串口接收 → 写入共享变量。这段延迟通常在 1-3ms 量级。目前 RM 主流实践中普遍不单独补偿 IMU 延迟——因为 1-3ms 对姿态角的影响（在目标移动速度 ~3m/s、云台转速 ~300°/s 时）远小于图像处理延迟和弹丸飞行时间的影响。

如果你需要补偿，方法和场景 2 完全一样：在 IMU 姿态队列里根据时间戳插值。这是下一步 §3.4.3 的 IMU 对齐策略的基础。

#### 3.4.3 多源时间对齐：相机为主时钟，其他信息向它看齐

这是本场景的算法核心。你的三个信息源——相机帧、IMU 姿态、机器人状态——在物理上是异步的，你必须决定"以谁的时间为基准"。

**基本原则**：真正为你提供敌方状态更新的信息源是相机帧。IMU 和机器人状态只是"辅助信息"——它们不告诉你敌人在哪，只告诉你机器人自身的姿态和比赛状态。因此：

> **以相机帧为主时钟。每拿到一帧图像，就创建一个处理任务；该任务中用到的所有其他信息，都要向图像帧的时间戳对齐。**

具体实现：

**① 对齐机器人状态（RobotStatus）：加锁读最新**

机器人状态变化很慢（比赛阶段切换、血量更新都是秒级的事情），不需要精确到毫秒级对齐。直接加锁读取串口线程维护的最新 `RobotStatus` 即可。

```
图像到达时刻 t_image
→ 加锁 → 读取 RobotStatus 的最新值 → 解锁 → 使用
```

**② 对齐 IMU 姿态：维护时间戳队列，四元数插值**

这是最需要精确处理的一项。IMU 以固定频率（如 200Hz = 每 5ms 一包）上报姿态数据。当你拿到一帧 `t_image` 时刻的图像，IMU 队列里可能有 `t_imu_1 = t_image - 3ms` 和 `t_imu_2 = t_image + 2ms` 的两包数据——你需要一个"在 t_image 时刻，IMU 的姿态应该是多少"的估计。

```
IMU 姿态队列（按时间戳排序）:
  ...  [t=100ms, q1]  [t=105ms, q2]  [t=110ms, q3]  ...

当图像帧在 t_image = 107ms 到达时:
  找到最接近的两帧: q2(105ms) 和 q3(110ms)
  插值权重: α = (107 - 105) / (110 - 105) = 0.4
  插值姿态: q_image = Slerp(q2, q3, α)
  其中 Slerp 是四元数球面线性插值（Spherical Linear Interpolation）
```

**Slerp 的直觉**：普通的线性插值 `lerp(a, b, α) = a + α(b - a)` 在两个四元数之间走的是"直线"——但这会让中间值偏离单位四元数球面。Slerp 在两个四元数之间走的是球面上的"最短弧"，保证插值结果仍然是合法的单位四元数（即合法的旋转）。

> **参见**：sp25 开源实现中的 IMU 队列和 Slerp 代码。

**③ 对齐延迟链**：让 process_latency 参与预测

对齐了数据之后，延迟链也被补上了关键一环。回顾场景 2 建立的完整延迟模型：

```
total_delay = process_latency + send_latency + comm_latency + fly_time
                ↑                  ↑              ↑              ↑
          本场景建立基础     场景 2 已完成   实车兜底超参   场景 7 引入
```

`process_latency = now() - data->time`（即从图像到达时刻到当前 Planner 执行时刻的耗时）。这一步的物理意义是：**当 Planner 在做预测时，它拿到的目标状态实际上是 `process_latency` 毫秒前的状态——目标已经在这段时间里移动了一段距离。** 因此在做前向预测时，必须把 `process_latency` 也算进总的前向预测时间窗口中。

> **参见 ALGORITHM_GUIDE.md §3.3** Sensor 阶段的时间戳记录，以及 §3.8.6 Planner 流程。代码中 `process_latency` + `comm_latency` + `fly_time` 三项为实际预测窗口（`send_latency` 归入 `comm_latency` 统一补偿），参见 `planner/Planner.cpp#L371`。

#### 3.4.4 整个传感器数据采集链的总览

经过本场景的改造，你的传感器→算法数据流如下：

```
物理世界                         上位机内存
──────────                    ──────────────
相机曝光/读出/传输 ──────────► cv::Mat frame  + timestamp (t_image)
                                  │
IMU 采样 → 单片机滤波 → 串口 ──► IMU 队列      + timestamps[]
                                  │
裁判系统 → 单片机打包 → 串口 ──► RobotStatus    (加锁共享变量)
                                  │
                                  ▼
                         每一帧以 t_image 为主时钟:
                           ├── 取最新 RobotStatus (加锁)
                           ├── 从 IMU 队列 Slerp 出 t_image 时刻的姿态
                           └── 进入算法链 (Detect → PnP → KF → Planner)
```

### 3.5 现在我们能做什么

**系统新增能力**：
- 相机采集时精确记录了图像到达时刻的时间戳 `data->time`
- 多源异步数据（图像/IMU/机器人状态）通过相机主时钟完成了时间对齐
- IMU 姿态通过 Slerp 实现了与图像帧的亚帧率级插值对齐
- 延迟链中 `process_latency = now() - t_image` 已建立，为后续场景 6 的流水线优化打下基础

**仍存在的局限**：
- 你的相机会产生运动模糊——我们还没处理曝光控制和镜头选型（场景 4）
- 你的 KF 观测值仍然来自"完美 YOLO 角点 + 完美 PnP"——感知精度还没被挑战（场景 5）
- 你的算力仍然是无限的——我们还没处理推理耗时和流水线（场景 6）

**实践练习**：
1. 在你的相机 SDK 获取图像的代码中，确认 `data->time` 是在拿到 `cv::Mat` 的瞬间记录的，而不是在图像预处理之后
2. 写一个简单的 IMU 队列类：`push(timestamp, quaternion)` + `query(timestamp) → Slerp插值结果`，用 200Hz 仿真数据测试插值精度
3. 在你的主循环中打印 `process_latency`（从 `data->time` 到当前时间的耗时），观察它的量级和抖动——这是场景 6 流水线化的数据依据


## 场景4
### 4.1 我们从哪里来

在场景 3 结束时，你的自瞄系统能够：
- 精确记录每一帧图像的到达时间戳 `data->time`
- 以相机为主时钟，将 IMU（Slerp 插值）和机器人状态（加锁读最新）对齐到同一时刻
- 建立了 `process_latency` 的概念（图像到达 → 当前时刻的累积耗时）

但所有这些能力都建立在一个前提下：**你的相机和镜头是"透明"的**——你假设图像是清晰的、角点是可辨识的、3D 世界到 2D 图像的映射是精确已知的。在真实世界中，相机不是一个完美的光子计数器——它是一组复杂的光学-电子-机械系统，你如何配置它，直接决定了你的算法能"看到"什么质量的画面。

仍在生效的理想约束：
- ~~C5：理想通讯~~（场景 2）
- ~~C3：理想传感器~~（场景 3 已解决时间对齐，本场景解决光学质量）
- C4：理想感知 / C6：无限算力 / C2：理想执行机构 / C1：单目标

### 4.2 这次放松什么约束

- **进一步放松约束 C3（光学成像）**：相机采集到的图像会模糊。

这不是"相机坏了"——这是物理定律决定的。具体来说：

1. **运动模糊**：曝光时间不是零。在快门打开的几百微秒到几毫秒里，你和目标都在移动。目标在画面上的像在曝光期间划过了一段距离——这就是运动模糊。
2. **景深限制**：镜头只能在某一个距离上完美对焦。离这个距离越远，成像越模糊。RM 的目标可能出现在 1m 到 8m 的任意距离——你不能同时让所有距离都清晰。
3. **光学畸变**：镜头不是完美的。画面边缘的直线会弯曲（径向畸变），画面会产生梯形失真（切向畸变）。不校正这些畸变，PnP 解算就会有系统误差。
4. **相机与云台的几何关系不精确**：相机不是焊在云台旋转中心上的。你如何精确知道相机坐标系相对于云台坐标系的位置和朝向？这个"外参"如果错了，你的整个坐标变换链就是从错误起点出发的。

### 4.3 新的任务是什么

> **让你的相机系统（相机 + 镜头 + 装配 + 标定）产出的图像质量和几何精度，足以支撑场景 1-3 中建立的全部算法链。**

这是一个结构 + 算法交叉的场景。你不需要推导新的数学公式，但你需要做一系列**不可跳过的工程决策**：

1. **相机选型**：用什么样的相机？
2. **镜头选型**：用什么样的镜头？
3. **光学调优**：光圈开多大？对焦对多远？曝光设多少？
4. **内参标定**：如何精确获得 `(fx, fy, cx, cy)` 和畸变系数？
5. **外参标定**：如何精确获得 `R_camera2imu` 和 `T_camera2imu`？
6. **机械装配**：如何确保相机和云台的几何关系稳定可靠？

### 4.4 怎么解决

> **本场景涉及的核心技术**：相机选型（靶面/像元/帧率） · 镜头选型（焦距/视场角） · 光圈与景深计算 · 曝光时间控制 · 内参标定 · 外参标定（手眼标定） · 机械定位与装配

> **🟡 协作模式说明**：本场景的内容大量依赖实战硬件经验和赛场调试直觉。以下内容由笔者（项目作者）的口述经验整理而成。不同队伍的具体硬件选择可能不同，但决策逻辑和物理约束是通用的。

#### 4.4.1 相机选型：三个参数决定一切

工业相机有三个关键参数：

1. **靶面尺寸**：RM 主流 Type 1/1.8 到 Type 1/3
2. **像元尺寸**：4μm 附近
3. **帧率**：150fps ~ 300fps

> **经验法则**：这三个参数彼此制约——靶面越大，进光量越足但配同视场角需更长焦距；像元越大，感光度越好但同靶面下分辨率降低；帧率越高，时间精度越高但曝光时间上限越低。
> **典型选择**：
>>   hikrobot MV-CU013-A0UC：（上科大26自瞄相机）
>   像元尺寸	4.8 μm×4.8 μm
>   靶面尺寸	1/2”
>   分辨率	1280 × 1024
>   最大帧率	201.4 fps@1280 x 1024 Bayer GB 8
> 
> >   hikrobot MV-CS016-10UM/C V5：（rv系主流选择）
>   像元尺寸	3.45 µm × 3.45 µm 
>   靶面尺寸	1/2.9”
>   分辨率	1440 × 1080
>   最大帧率	249.1 fps @1440 × 1080 Bayer RG 8 

#### 4.4.2 镜头选型：焦距

镜头焦距和靶面尺寸一起决定了视场角（FOV）。你可以让 LLM 帮你算。RM 的步兵主流镜头（典型目标距离 3 米，最远一般能看清 5m 左右的目标）一般是：

1. Type 1/1.8 配 **8mm**
2. Type 1/3 配 **6mm**

如果你要看的更远，你需要更长的焦距。

注意“适配靶面尺寸”和“光圈”也是镜头的参数。你要：
1. 镜头设计靶面尺寸不小于相机真实靶面尺寸。
2. 具有合理的光圈，数值见下。光圈太大的镜头一般体积和重量也会比较大。
3. 作为参考，上科大26年采取一款8mm 设计靶面1/1.8 f2的镜头，重约30g。

#### 4.4.3 光学调优：光圈、对焦、曝光

这三项是纯物理操作——没有代码、没有算法，但你做错了，后面的一切都白费。

**① 光圈（Aperture）**

光圈越大，画面越明亮，但是景深越浅。反过来——光圈越小（F 值越大），景深越深，但画面变暗。

> **经验法则**：RM 典型光圈 **F2 ~ F2.8**（工业镜头开到比较大或最大）。你可以告诉 LLM 你的：目标典型距离、目标最远和最近距离、靶面尺寸、分辨率。让它帮你计算多大光圈下依然能保持从最远到最近都清晰。

**② 对焦（Focus）**

对焦到典型目标距离上。用紧定螺丝固定光圈和对焦——最佳实践是**用布基胶带完全固定**，比赛中的震动会让一切没固定紧的东西松动。

**③ 曝光时间（Exposure）**

曝光时间越长 → 画面越亮，但运动模糊越严重。

> **经验法则**：一般我们认为曝光时间超过 **3000**（μs）会导致画面模糊。你可以让 LLM 帮你根据目标移动速度计算模糊量来调整。

#### 4.4.4 内参标定：为什么不能跳过

相机的内参矩阵 K 是 PnP 解算的必要输入——它告诉你"从像素坐标到归一化相机坐标的映射"。标定内参就是用已知尺寸的标定板，拍摄多角度照片，用张正友标定法求解 K 和畸变系数。

```
K = [fx   0   cx]
    [0   fy   cy]
    [0    0   1 ]

畸变系数: [k1, k2, p1, p2, k3]
```

> **经验法则**：选一个好的标定板，好好爱护。劣质标定板（打印精度差、表面不平整、棋盘格尺寸不准）会明显影响标定结果——最终影响的是你的 PnP 解算精度，也就是弹着点偏差。实在没有物理标定板时，可以用平板或便携屏显示标定图案。

标定完成后，将参数保存在 YAML 文件中（参见 ALGORITHM_GUIDE.md §5.1 中的 `camera_para` 配置项）。

#### 4.4.5 外参标定：相机和云台之间的"翻译官"

外参 `(R_camera2imu, T_camera2imu)` 描述相机坐标系相对于云台坐标系的位置和朝向。这个参数错了，你计算出的"目标在世界系中的位置"就系统性地偏了。

在场景 1 的模块 3 中，坐标变换链的 Step 2 就是：

```
P_imu = R_camera2imu × P_camera + T_camera2imu
```

> **参见 ALGORITHM_GUIDE.md §3.7.2** 中完整的坐标变换三步链（图像→相机→IMU→世界）。

**两种标定方法**：

| 方法 | 思路 | 优点 | 缺点 |
|------|------|------|------|
| **手眼标定** | 云台转动多个角度，同时拍摄固定参照物（如标定板），解算相机与云台旋转中心的相对位姿 | 精度高，可复现 | 操作复杂，需要标定板 |
| **打弹微调** | 问机械同学要到相机和云台旋转中心之间的大致平移关系，然后一边打弹一边微调 `T_camera2imu` 直到弹着点与瞄准点重合 | 直观，直接验证最终效果 | 依赖散布稳定，需要场地和弹药 |

> **参见**：手眼标定的具体实现参考 sp25 开源。机械臂手眼标定的数学本质是 AX = XB 问题。

#### 4.4.6 机械装配：让相机和云台之间的关系靠谱

前面的算法再精确，如果相机在云台上是**晃动**的，一切白费。

> **经验法则**：相机与云台核心旋转部分必须具有高刚度的稳固连接——晃动是坏的。每次拆装后相机与云台的几何关系必须一致——这需要机械同学设计好合理的定位槽或其他定位体系。

> **参考**：23 年上海交通大学平衡步兵开源——关于什么是好的相机装配的工程范例。

#### 4.4.7 决策流程总览

将以上六步串联成一条决策链：

```
1. 根据兵种和预期交战距离 → 确定靶面 + 焦距
2. 硬件到货后 → 安装并调光圈（F2-F2.8）→ 对焦到典型距离 → 固定
3. 根据场地光照和运动分析 → 设定曝光时间（≤ 3000μs）
4. 用标定板 → 标定内参 → 保存 YAML
5. 用手眼标定或打弹微调 → 标定外参
6. 确保机械装配稳固、可复现 → 完成
```

**系统新增能力**：
- 相机系统经过完整选型、安装和光学调优，在典型交战距离产出清晰、低模糊的图像
- 内参 K 和畸变系数已精确标定，PnP 解算不再有系统性的几何误差

## 场景5
### 5.1 我们从哪里来

在场景 4 结束时，你的自瞄系统能够：
- 相机/镜头经过完整选型、安装和光学调优，产出清晰、低模糊的图像
- 内参 K + 畸变系数精确标定，外参 `(R_camera2imu, T_camera2imu)` 可靠
- 从图像到世界坐标的几何链路在理论上是精确的

但你还没有面对一个核心事实：**你输入给 PnP 的角点是神经网络输出的，而神经网络不是完美的。** 场景 1-4 一直假设 C4（理想感知）成立——YOLO 输出的 4 个角点精确落在装甲板的四个顶点上。现在这个假设要碎了。

仍在生效的理想约束：
- ~~C5：理想通讯~~（场景 2）
- ~~C3：理想传感器~~（场景 3/4）
- C4：理想感知（**本场景将解决**）
- C6：无限算力 / C2：理想执行机构 / C1：单目标

### 5.2 这次放松什么约束

- **放松约束 C4（感知精度）** + 进一步放松 C3：

在真实世界中：

1. **大角度的装甲板角点会被遮挡**：当装甲板侧对你时，远离你的那条灯条会被装甲板自身挡住。神经网络此时只能"猜"被遮住的角点——猜错是常态。
2. **神经网络（尤其是量化后）的角点不是完全精准的**：YOLO-Pose 输出的 4 个关键点有像素级偏差（典型 1-3 像素）。当你用这些有偏差的角点做 PnP 时，解出的几何位置和 yaw 也会有偏差。结果组装为 `[y, x, z, yaw]` 后进入滤波器，距离越远，角点误差被杠杆放大的倍数越大。

一句话：**感知误差从源头污染了整个下游。** KF 的观测值不再可信、PnP 的位姿不再精确。如果不管，你会瞄准一个"神经网络认为装甲板所在的位置"而非"装甲板真实所在的位置"。

### 5.3 新的任务是什么

> **在角点存在像素级误差、大角度时存在遮挡的前提下，尽可能恢复出装甲板的真实 3D 位姿，作为 KF 的可靠观测输入。**

本场景拆为两个子章：

| 子章 | 主题 | 核心问题 |
|------|------|---------|
| **5A** | 从像素误差到精准位姿 | 怎么得到更准的角点？怎么基于不完美的角点算出更可靠的 3D 位姿？ |

#### 5.4.1 子章 5A：从像素误差到精准位姿 — 探测模块、角点精修与 PnP 降自由度优化

> **本子章涉及的技术**：真实探测模块的三种方案 · PCA 角点矫正 · 三分法 PnP 降自由度优化（固定 pitch/roll，优化 yaw）

##### 5A.1 真实探测模块：三种方案的选择

你的 YOLO-Pose 在场景 1 中是"完美的"——但在真实世界中，它输出的角点有像素级偏差，大角度下还会被遮挡。针对这个问题，社区有三种主流实现方案。

| 方案 | 核心思路 | 优点 | 缺点 |
|------|---------|------|------|
| **纯传统视觉** | 不依赖神经网络——灰度二值化 → 找轮廓 → 配对灯条 → 传统方法找角点 | 不依赖 GPU/NPU；角点精度可控；光照稳定时可靠性高 | 光照鲁棒性弱；大角度遮挡下灯条配对困难；无法识别数字 |
| **纯神经网络** | 完全依赖 YOLO-Pose，用足够大的数据集和模型容量硬堆精度 | 端到端简单；光照和大角度鲁棒性强；同时给出角点 + 颜色 + 标号 | 需要大量标注数据（≥ 5000 张）；量化后精度下降；NPU 依赖 |
| **神经网络 + 区域传统优化** | YOLO 找大致区域和角点 → 在每个灯条区域上用传统方法精修角点 | 兼顾神经网络鲁棒性和传统方法精度；int8 量化后也能用传统优化补救 | 实现复杂度最高；需要维护两套代码路径 |

**方案选择建议**：如果你的算力充足且有 GPU，方案 B（纯神经网络）训练充分后最简单。如果你需要使用 NPU int8 量化推理，方案 C（神经网络 + 传统优化）是主流选择——先用 YOLO 找到灯条的大致位置，再在灯条局部区域上用传统方法精修角点。如果你的计算平台完全不支持神经网络推理，方案 A 是唯一选择。

##### 5A.2 传统视觉探测的经典流程（方案 A 参考）

以 RM 社区广泛参考的中南大学 2024 开源方案为例，传统视觉装甲板探测的完整流程如下：

```
输入图像 (BGR)
  │
  ├── Step 1: 预处理
  │   转灰度图 → 固定阈值二值化 (binary_thres)
  │   理由：工业相机动态范围有限，灯条中心常过曝 R=B，
  │         直接用灰度二值化比颜色二值化更稳定
  │
  ├── Step 2: 找灯条 (findLights)
  │   findContours → minAreaRect 外接矩形 →
  │   筛选条件：长宽比 (min_ratio ~ max_ratio) + 倾斜角 < max_angle
  │   颜色判断：轮廓内 sum(R) > sum(B) → 红色灯条，反之蓝色
  │
  ├── Step 3: 配对灯条 (matchLights)
  │   两两配对 → 排除包含关系 → 筛选条件：
  │   两灯条长度比 > min_light_ratio +
  │   中心距离在 [min_center_distance, max_center_distance] +
  │   配对倾角 < max_angle
  │
  ├── Step 4: 数字识别 (extractNumbers + Classify)
  │   透视变换 → ROI → 大津法二值化 → LeNet-5 分类
  │
  └── 输出：装甲板 bbox + 角点 + 颜色 + 标号
```

> **参考**：24 年中南大学开源（`rm_auto_aim/armor_detector`），该方案在华南师范大学 `rm_vision` 基础上增加了 PCA 角点矫正和灰度二值化等改进。下文角点精修部分主要跟随中南方案介绍。

##### 5A.3 角点精修：PCA 矫正灯条端点

传统视觉中用旋转矩形的顶点作为灯条角点（如 minAreaRect 的四个角），但这存在一个明显问题：**二值化阈值不同、光照不均匀时，旋转矩形的顶点位置会漂移**——角点的实际坐标与 `types.hpp` 中定义的装甲板模型点不匹配，直接影响 PnP 精度。

中南方案使用 **PCA（主成分分析）** 方法解决这个问题：

```
对于每个灯条（轮廓内的点集）：
  │
  ├── Step 1: PCA → 得到灯条的对称轴方向（第一主成分）
  │
  ├── Step 2: 沿对称轴方向，向上下两个方向搜索
  │   寻找亮度变化最大的点（灯条边缘的明暗交界处）
  │
  └── Step 3: 以这两个明暗交界点作为灯条的角点
```

这种方法的核心优势：**角点定位不再依赖二值化阈值的偶然性**——PCA 从点集的整体分布中提取方向，明暗交界是物理固有的亮度跳变，不随二值化阈值漂移。

> **参考**：PCA 角点矫正来自 24 年中南大学开源方案。26 年上海科技大学开源方案中的"神经网络 + 区域传统优化"本质上也使用了类似的局部精修策略——先用 YOLO 框出灯条，再在局部区域做 PCA 矫正或边缘搜索。

##### 5A.4 PnP 降自由度：固定 pitch/roll，用三分法优化 yaw

角点精修后，你有了更准的 2D 角点。但 PnP 解算还有一个更深层的优化空间——**降自由度**。

回顾场景 1 的模块 3：我们直接把 6D 位姿降为 4D `(x, y, z, yaw)`，因为装甲板的 pitch ≈ 15°、roll ≈ 0° 是机械规则决定的常量。实际传给滤波器的 4D 观测按 `[y, x, z, yaw]` 排列，但仍包含 4 个被估计的自由度。`(x, y, z)` 是 PnP 解的平移量，`yaw` 是旋转角。在角点有误差时，**同时估计 4 个量意味着误差会在它们之间分摊**——平移的误差会"泄漏"到 yaw 的估计中，反之亦然。

降自由度优化的核心思路是：**固定已知的约束，只在最不确定的维度上优化。**

具体来说：
- 装甲板的 pitch 固定为 15°（由 RM 制作规范决定）
- 装甲板的 roll 固定为 0°（平行地面）
- 装甲板的平移 `(x, y, z)` 由 PnP 解出的 tvec 提供（即使有误差，tvec 的量级基本可信）
- **唯一需要精细优化的是 yaw**——因为 yaw 对像素角点的朝向误差最敏感

数学上，降自由度优化就是一个 **1D 最小化问题**：

```
给定：PnP 解出的平移 tvec + 装甲板模型点 + 相机内参
      图像中检出的 4 个角点 pus[4]
      神经网络给出的 yaw 初值

目标：找到一个 yaw 值，使得——
      用 (yaw, pitch=15°, roll=0°) 构造的装甲板 3D 角点
      → 重投影到图像上
      → 与检出角点的像素误差最小

代价函数形式：
  cost(yaw) = Σ_i || pus[i] - project(R(yaw) × P_3D[i] + tvec) ||²

求解：在 yaw 的合理范围内 [yaw_min, yaw_max]
     用三分法（Trisection）或 Ceres 等数值优化迭代求解
```

这个优化问题的输入是 4 个 3D 模型点 + 4 个对应图像角点 + 已知的 pitch/roll，**唯一的自由变量是 yaw**。相比标准的 solvePnP 同时估计 6 个自由度，降为 1D 后求解稳定性大幅提高——在数值优化中，1D 搜索空间几乎不可能发散。

**单装甲板 vs 双装甲板的处理**：

当视野中只看到 1 块装甲板时（`fit_single_z_to_v`），优化范围基于"装甲板可见角度"的几何约束确定：
```
z_to_v_min = max(π - must_not_see_angle, π + must_see_angle - angle_between_armors)
z_to_v_max = min(π + must_not_see_angle, π - must_see_angle + angle_between_armors)
```

当视野中同时看到 2 块装甲板时（`fit_double_z_to_l`），两块装甲板互为约束——它们的 yaw 相差 `angle_between_armors`（相邻装甲板对的夹角 = 2π / 装甲板总数），使用两块板的角点同时构造代价函数，进一步压缩 yaw 的估计方差。

> **代码参考**：`fit_single_z_to_v` 和 `fit_double_z_to_l` 的完整实现见 `predictor/motion/top_model.cpp`。核心是 `radial_armor_pts()` 将假设的 yaw 值转为重投影角点，`get_pts_cost()` 计算与检出角点的加权像素误差（在"沿灯条方向"和"垂直灯条方向"上使用不同的误差权重——前者容忍度更高，后者惩罚更严格，因为神经网络在垂直于灯条的方向上角点误差更大）。

> **参见 ALGORITHM_GUIDE.md §3.6** CornerRefine 阶段中 `ArmorCornerOptimizer` 的角点精修算法，以及 §3.7.2 坐标变换与 PnP 定位流程。

```
data->bboxes[] (YOLO 原始角点, 有误差)
  │
  ├── [方案选择] 纯传统 / 纯NN / NN+传统优化
  │   根据算力平台和数据集决定
  │
  ├── [角点精修] PCA 矫正 / 边缘搜索

  │

  │

```

##### 5A.6 5A 阶段小结

5A 完成了从像素到精准 4D 观测的优化链路。你现在拥有了：三种可选探测方案的知识、PCA 角点矫正消除二值化漂移的能力、以及 PnP 降自由度优化（固定 pitch/roll，三分法优化 yaw）大幅提高 yaw 估计精度的方法。单板和双板场景各有对应的优化策略。

**但**：4D 观测 `[y, x, z, yaw]` 仍然不是完美的。角点精修和降自由度优化降低了误差，但不能消除它。当这些残余误差进入 KF 时，场景 1 中建立的 4 个独立 1D 线性 KF 的假设（观测噪声是均匀的、各向同性的）不再成立。5B 的任务是升级 KF，使其能处理**真实的噪声结构**。

#### 5.4.2 子章 5B：从位姿观测到稳定跟踪 — EKF 升级、马氏距离匹配与噪声建模

> **本子章涉及的技术**：非各向同性观测噪声模型 · 匀速白噪声过程模型（Piecewise White Noise） · 马氏距离匹配 · IESEKF（迭代扩展卡尔曼滤波）
>
> **本节聚焦**：EKF 的参数不是凭空设定的——**每个参数都来自观测器和目标的物理特性**。本节的重点是教你如何从物理直觉出发，观测、统计并计算出这些参数。

##### 5B.1 为什么需要升级 EKF — 两件独立的事

在思考"为什么要从场景 1 的 4×1D KF 升级到 EKF"时，很容易把两个不同的问题混在一起。让我们把它们拆开：

**问题 A：观测噪声不是各向同性的 → 需要合理地设置 R 矩阵**

这是 §5B.2 和 §5B.3 要解决的事。无论目标是否旋转、无论你用 4D 装甲板模型还是 11D 整车模型，你拿到的观测值都按 `[y, x, z, yaw]` 排列，并来自 PnP 解算。PnP 的误差在不同方向上是不同量级的，深度方向远大于横向。这意味着即使你保持装甲板模型 KF 不变，也需要把每个轴的观测噪声设成不一样的，不能再像场景 1 那样 4 个独立 KF 各用一个统一的标量 R。

一句话：**噪声非各向同性 → 需要精心设置 R。这事和模型维度无关。**

**问题 B：目标高速原地旋转（小陀螺）→ 需要从 4D 升级到 11D 整车模型**

这是为什么要换模型。回顾场景 1 的双模型概念（§1.4 模块 4）：单装甲板模型跟踪的是一块板的几何位置和 yaw，传入滤波器的观测顺序为 `[y, x, z, yaw]`。当目标只做平移时，这块板子的位置变化可以用匀速模型近似。但当目标高速自转（小陀螺）时：

- 你看到的装甲板在快速切换（四块板交替出现在视野中）——单装甲板模型的观测在"跳跃"，匀速假设被暴力打破
- 装甲板的运动不是平移，而是**圆周运动**——它的 `(x, y)` 轨迹是一个圆，圆心是车辆的旋转中心
- 圆周运动在笛卡尔坐标系下是**高度非线性的**——`x = R × cos(θ), y = R × sin(θ)`——线性 KF 的匀速外推完全无法捕捉

因此你需要一个**整车模型 EKF**：在状态中增加旋转中心 `(x_center, y_center)`、旋转半径 `r`、转速 `vyaw`，让滤波器直接跟踪"车辆怎么转"，而不是"一块板子飘到哪"。这需要 11 维状态向量（见 ALGORITHM_GUIDE §3.7.3）和能处理非线性观测的 EKF（而非线性 KF）。

一句话：**小陀螺 → 装甲板圆周运动 → 高度非线性 → 需要 11D 整车 EKF。这事和噪声无关。**

**本场景直接面对高速旋转目标。** 从 C1 约束被放宽的那一刻起（目标不再只是低速平移的步兵，而是可以高速自转的任意兵种），4D 匀速装甲板模型就失效了——你必须在场景 5 就引入 11D 整车 EKF。这就是为什么本节同时讲解 R/Q 噪声建模（应对 A）和完整的 EKF + 马氏距离 + IESEKF 架构（应对 B）。

##### 5B.2 非各向同性观测噪声：R 矩阵的物理来源

在卡尔曼滤波中，**观测噪声协方差矩阵 R** 描述了你对观测值的不信任程度。在场景 1 的线性 KF 中，每个 1D 滤波器有一个标量 R。在 EKF 中，R 是一个 4×4 矩阵。

**噪声天然的坐标系不是 XYZ，而是 YPD（球坐标）。**

想一想噪声的物理来源：像素抖动最直接的影响是**方位角误差**和**俯仰角误差**（各是多少弧度），以及**深度估计误差**（PnP 解算的 tvec 在视线方向上的不确定度，通常随距离线性增长）。这些天然在 **球坐标系（Yaw-Pitch-Distance，简称 YPD）** 下是对角的、互相独立的。

但你的 EKF 观测向量是 `(y, x, z, yaw)`——在笛卡尔坐标系下。因此你需要把对角的 YPD 噪声旋转到 XYZ 空间。

**从物理参数到 YPD 噪声**

你首先需要 4 个物理参数——它们都可以从传感器和场景物理特性推算出：

| 参数 | 含义 | 典型值 | 怎么得到 |
|------|------|--------|---------|
| `std_dev_azi_angle` | 方位角（水平）标准差 | ~3.6° → 0.063 rad | 1 像素抖动 ÷ 焦距 ≈ 角分辨率 |
| `std_dev_ele_angle` | 俯仰角（垂直）标准差 | ~3.6° → 0.063 rad | 同上，垂直方向 |
| `std_dev_dist_coeff` | 深度噪声系数 | ~0.05~0.20 | 距离越远 PnP 深度越不准；可以统计不同距离下的 tvec 抖动来拟合 |
| `std_dev_tgt_yaw` | 装甲板朝向角标准差 | ~17° → 0.3 rad | NN 解算 yaw 的本征精度，大角度遮挡时更大 |

> **参见 ALGORITHM_GUIDE.md §3.7.3** 中观测噪声模型的物理含义（方位角 3.6° / 俯仰角 3.6° / 距离 20% / yaw 20°），这些是 `std_dev_*` 的参考取值来源。

**从 YPD 噪声到 XYZ 协方差**

你不能直接把角度方差填进 XYZ 对角线——因为 1° 的方位角误差在空间中到底对应 X 轴多少米、Y 轴多少米，取决于目标在当前视野中的方位。做法是：

```
在 YPD 系下写出观测噪声（对角的、各通道独立的）：
  R_ypd = diag(σ_azi², σ_ele², σ_dist², σ_yaw²)

然后通过 YPD → XYZ 坐标变换的雅可比 J，将噪声从 YPD 旋转到 XYZ：
  R_xyz = J × R_ypd × J^T

其中 J = ∂(xyz)/∂(ypd) 在当前观测点处计算。
```

这个雅可比的核心效果是：**方位角噪声按弧长 `dist_3d × σ_angle` 投射到垂直于视线的水平方向，俯仰角噪声投射到高度方向，深度噪声投射到视线方向。** 然后通过当前相机姿态（注意：相机可能有 roll，所以俯仰角误差和高度误差之间并不是简单的 Z 轴独立关系——它们通过云台的当前 roll 角耦合）再统一旋转到世界 XYZ 系。

> **代码参考**：`predict/Tracker.cpp` 中 `whole_state_ekf_init()` 内的 `update_R_` 函数（行号约 730-785），使用径向/切向基向量外积的方式等价地实现了上述雅可比旋转。其中的 `std_dev_azi_angle` 等参数可通过滑动条实时调节（`update_parameter()` 函数）。

**物理直觉**：
- 噪声在 YPD 下是**对角的**（三个角度/深度噪声独立），在 XYZ 下是**满的**（非对角项不为零），因为同一个角度抖动通过雅可比同时投影到了 X 和 Y 坐标上
- 噪声量随距离线性放大（弧长 = r × θ），所以 R 矩阵是**动态的**——每帧根据目标的当前位置重算，不是静态常量
- 相机 roll 角会导致俯仰角误差不再只影响 Z——它通过旋转矩阵耦合进 XY 平面。在 roll 接近零时，俯仰 → Z 的耦合近似独立，但 roll 较大时必须完整计算雅可比

##### 5B.3 过程噪声模型：Q 矩阵与 Piecewise White Noise

R 回答了"我不相信观测多少"。**过程噪声协方差矩阵 Q** 回答了另一个问题："我不相信我的运动模型多少。"

在场景 1 的线性 KF 中，我们假设目标做匀速运动。EKF 同样假设匀速，但**承认这个假设不完全准确**——目标可能加速、可能转向。Q 矩阵量化的就是这个"模型不完全准确"的程度。

sp25 实现使用 **Piecewise White Noise Model**（分段白噪声模型）来构造 Q。其物理假设是：**目标的加速度是一个分段常数，在每一段内以为白噪声形式随机变化。** 白噪声的强度由加速度方差参数描述。在本项目中，对应的参数为 `p_coord`（平移加速度方差）、`p_yaw`（角加速度方差）、`p_r`（旋转半径变化方差）。

```
对于状态 [x, vx] —— 匀速模型，加速度是"未建模的扰动"：
  x_{k+1} = x_k + vx_k * dt + 0.5 * a * dt²  （a 是未知加速度）
  vx_{k+1} = vx_k + a * dt

如果 a 是方差为 p_coord 的白噪声，则它在 dt 时间内对状态造成的协方差贡献为：
  Q_x = p_coord × [[ dt⁴/4,  dt³/2 ],
                    [ dt³/2,  dt²   ]]
```

在代码中（`predict/Tracker.cpp` `whole_state_ekf_init()`）：

```cpp
// Piecewise White Noise Model
double q_x_x = pow(dt, 4) / 4 * p_coord;
double q_x_vx = pow(dt, 3) / 2 * p_coord;
double q_vx_vx = pow(dt, 2) * p_coord;

// y/vx 块用 p_coord, x/vx 块用 p_coord, z/vz 块用 p_coord
// yaw/vyaw 块: 用 p_yaw 替代 p_coord
// r/dz/another_r 对角块: 用 p_r
```

**物理直觉**：
- `p_coord`：目标平移加速度白噪声强度。值越大，KF 越愿意让位置估计快速跟随新观测；值越小，KF 越坚持匀速假设（轨迹更平滑但滞后更大）
- `p_yaw`：目标角加速度白噪声强度。值越大，转速估计越灵活；值越小，转速估计越稳定但难以捕捉突然的转速变化
- `p_r`：旋转半径和高差的变化方差。通常设得较小——因为机械上半径和高差不会突变
- Q 矩阵中 `r`、`dz`、`another_r` 对角块使用 `p_r`（非零），这与 sp25 中将其设为零不同——本项目允许这些参数在观测下缓慢收敛

> **数值参考（来自 sp25 开源）**：sp25 中 `v1=100`（平移加速度方差）意味着 `σ_a = √100 = 10 m/s²`——即你预期目标平移加速度的标准差约为 10 m/s²（约 1g），对应步兵 1 秒内速度变化 ±10 m/s 的机动能力。`v2=400`（角加速度方差）意味着 `σ_α = √400 = 20 rad/s²`——即你预期目标角加速度的标准差约为 20 rad/s²（约 3.2 转/s²），对应小陀螺从静止到达满转速的响应速度。这些数值可作为你标定 `p_coord` 和 `p_yaw` 的量级参考——如果你的目标兵种机动能力不同，相应地缩放这些参数。

##### 5B.4 马氏距离匹配：用协方差做"聪明的门禁"

5A 产出的 4D 观测进入 EKF 后，EKF 会输出一个**预测值** `z_pred`（基于上一帧状态 + 运动模型外推的"观测应该是什么"）。当下一帧真的来了一个观测 `z_meas` 时，你需要判断：**这个观测和当前的跟踪目标是同一个东西吗？**

场景 1 中隐含使用的是**欧氏距离**：`||z_meas - z_pred|| < threshold`。但欧氏距离有一个致命缺陷——它把所有维度一视同仁。而你已经知道（§5B.2），深度方向的噪声远大于角度方向。用欧氏距离意味着一个深度方向上的小偏差（可能是噪声）和一个角度方向上的大偏差（可能是"换目标了"）被同等对待——这会导致两个问题：

1. **门限太宽**：为了容忍深度方向的大噪声，阈值必须设得很大 → 角度方向上明明已经换目标的观测也被放进来
2. **门限太窄**：为了在角度方向上敏感地检测目标切换，阈值设得很小 → 深度方向正常的噪声抖动也会被拒绝

**马氏距离（Mahalanobis Distance）** 解决了这个问题。它在做距离计算时，**用预测协方差 S 作为"尺度"来归一化每个维度**：

```
马氏距离:  d² = (z_meas - z_pred)^T × S⁻¹ × (z_meas - z_pred)

其中 S = H × P × H^T + R
  H  — 观测矩阵（状态 → 观测的线性化映射）
  P  — 状态协方差矩阵（你对状态估计的不确定度）
  R  — 观测噪声协方差矩阵（§5B.2）
```

**物理直觉**：S 可以理解为一个"误差椭球"——它描述了"在当前状态下，下一帧观测会落在哪个区域"。马氏距离衡量的是"观测点离这个椭球中心有几倍椭球半径"。

- 如果深度方向的噪声大，S 在深度维度上就"胖"——同样的欧氏偏差，在这个维度上马氏距离更小（更容易通过门限）
- 如果角度方向的噪声小，S 在角度维度上就"窄"——在这个维度上，马氏距离更敏感（更容易拒绝异常值）

**匹配阈值的选择**：马氏距离的平方在零假设（观测确实来自同一个目标）下近似服从卡方分布 χ²(4)（4 个观测自由度）。选择阈值使得正确的观测有高概率（如 95%）被接受——在 χ²(4) 下对应约 9.49。超过这个阈值的观测被视为"可能是另一个目标"或"噪声异常值"，不被用于更新当前跟踪器。

##### 5B.5 IESEKF：迭代让线性化"几乎免费"地更精确

标准 EKF 在更新步骤中对非线性观测函数 `h(x)` 只在预测值 `x_pred` 处做一次一阶泰勒展开：

```
h(x) ≈ h(x_pred) + H × (x - x_pred)
```

当 `x_pred` 离真实状态较远时（如跟踪初始化阶段、或目标突然变速时），这个一次展开的近似误差可能很大——导致 KF 更新后的状态反而偏离真相。

**迭代扩展卡尔曼滤波（IESEKF / IEKF）** 的做法是：在更新步骤中多次迭代——每次用更新后的状态重新计算观测矩阵 H，再做一次更新。形式上：

```
x^{k+1} = x_pred + K(x^k) × (z - h(x^k) - H(x^k) × (x_pred - x^k))
```

收敛后（通常 2-5 次迭代），相当于在**真值附近**做线性化——比只在预测值附近展开一次要精确得多。

**为什么说"几乎免费"？**

标准 EKF 的更新步骤本身就需要计算 H 和 K。IESEKF 只是**多算几次 H 和 K**——没有新的矩阵分解，没有更高维的优化。计算开销大约是多 2-5 倍的更新步骤耗时，相对于整条算法链（推理 + PnP + 全部 KF 预测/更新）来说几乎可以忽略。

> **参见 ALGORITHM_GUIDE.md §3.7.3** 中"基于 IESEKF 的迭代扩展卡尔曼"的完整规范。IESEKF 是标准 EKF 的自然升级——如果你的系统已经实现了 EKF，加入迭代循环是低成本的精度提升。

##### 5B.5.5 多装甲板观测：看到两块板时如何更新？

高速旋转的目标上，有时一帧能同时看到两对灯条——即两块装甲板。这就引出一个问题：**两块板能同时用来更新 EKF 吗？如果能，怎么更新才算正确？**

sp25 的实现是见到两块就更新两次——`update_target` 遍历所有匹配目标名称和类型的装甲板，每个都调用 `target_.update(armor)`，每次执行一次 `ekf_.update()`。这是一种朴素的做法。

**两次顺序更新是否等价于一次联合更新？**

标准 KF 中，对同一个预测值 `x_pred`，两次顺序更新（先观测 `z1`，再观测 `z2`）在数学上严格等价于一次联合更新（观测 = `[z1; z2]`），**前提是**：

1. 两次更新使用同一个线性化点 `x_pred`——即第二次更新不能用第一次更新后的状态来重新计算 `H` 和 `h(x)`
2. 两个观测的噪声独立（`R = diag(R1, R2)`，块对角）

但在 sp25 的 `Target::update_ypda` 中，第二次调用时 `H = h_jacobian(ekf_.x, id)` 用的是第一次更新**之后**的状态，而非最初的预测状态——相当于在两个不同的线性化点做了两次独立更新。这不是标准的顺序更新，也不是联合更新的等价形式。

**实践中这影响大吗？**

单帧内两次连续 EKF 更新的状态变化通常不大（一个观测信息量有限），线性化点的偏移对结果影响有限——实践中 sp25 使用这种做法效果很好。但它确实不是数学上严密的。

**fitted yaw 场景下的特殊问题**

§5A.4 中，`fit_double_z_to_l` 用两块装甲板联合优化 yaw——此时两块板的 yaw 观测来自同一个优化过程，它们的 yaw 噪声天然相关。如果使用联合优化后的 yaw 分别构造两块板的 4D 观测再做顺序更新，**存在 yaw 信息被重复计入的风险**——因为同一个优化结果通过两个通道各自更新了 EKF 的 yaw 相关状态。

**正确的做法**：

在实践中，有三种可接受的选择：

| 做法 | 描述 | 数学严密性 | 工程复杂度 |
|------|------|----------|-----------|
| **只用最佳单板** | 每帧只取最优匹配的装甲板做一次 EKF 更新 | ✅ 严格 | 最简单 |
| **顺序更新** | 对每块板依次调用 `ekf_.update()`（sp25 做法） | ⚠ 近似（线性化点偏移），实践中效果好 | 简单 |
| **联合更新** | 将两个 4D 观测堆叠成 8D，一次联合更新；若 yaw 联合优化过还需处理交叉相关 | ✅ 严格 | 复杂 |

对于 `fit_double_z_to_l` 场景，最稳妥的做法是只用联合优化后的 yaw 构造**一块板的 4D 观测**做单次更新——因为 yaw 的信息增益已经通过两板联合优化获得了，不需要再通过两块板的顺序更新"double dip"。如果你需要双板同时提供位置观测（好处是两块板的位置约束互为验证），可以考虑联合更新，但必须注意 yaw 维度的交叉相关。

> **代码参考**：sp25 中 `update_target` 的双板顺序更新逻辑见 `tasks/auto_aim/tracker.cpp`。本项目中，如果使用了 `fit_double`（场景 5A），建议仅用匹配到的最近装甲板做单次 EKF 更新。

##### 5B.6 小结：5B 的完整数据流

```
5A 输出: 4D 观测 [y, x, z, yaw] + 降自由度优化的结果

  │
  ├── [EKF 预测] 基于上一帧状态 + 匀速模型 + Q 矩阵外推
  │   过程噪声: Piecewise White Noise (p_coord / p_yaw / p_r)
  │   状态: 11 维 [y,vy, x,vx, z,vz, yaw,vyaw, r, another_r, dz]
  │
  │   其中 `another_r` 是另一组装甲板半径与 `r` 的差，`dz` 是两组装甲板的高度差。
  │
  ├── [马氏距离匹配] 用预测协方差 S 判断观测是否为同一目标
  │   d² = (z_meas - z_pred)^T S⁻¹ (z_meas - z_pred)
  │   阈值: 基于 χ²(4) 的 95% 置信界
  │
  ├── [IESEKF 更新] 迭代更新 (2-5 次)
  │   观测噪声 R: YPD 对角噪声 (σ_radial / σ_tangent / σ_z / σ_yaw)
  │               通过 u_radial/u_tangent 基向量外积旋转回 XYZ
  │   每次迭代在更新后的状态处重新计算 H 和 R
  │
  └── 输出: 11 维后验状态 + 协方差 P
         → 进入 Planner 做预测瞄准
```

> **参见 ALGORITHM_GUIDE.md §3.7.3** 中整车模型 EKF 的完整 11 维状态向量定义、跟踪器状态机、装甲板切换检测和模型可信度判断。

### 6.2 这次放松什么约束

- **放松约束 C6（算力约束）**：上位机的运算需要时间，而且算力有限。

这意味着你的算法链中的每一步都有真实的物理耗时。以上海科技大学2026年开源小电脑为例，它有8个A55核心，整体性能是比较弱的：

- 神经网络推理（YOLO-Pose-5n）：2 ms
- 前处理（resize/normalize）：3-4 ms
- 角点精修（传统视觉）：0.5-2 ms
- PnP 解算 + 降自由度优化：0.5-1.0 ms
- EKF 预测/更新（以及其他预测器开销）：2 ms
- Planner 规划 + MPC + 指令生成：2 ms
- **合计（单帧串行）**：约 10-15 ms

对于其他主流选择（amd 8845hs，intel 13400h），大部分cpu任务计算都会更快，但YOLO-Pose-5n的推理开销会成为瓶颈，约5ms。

如果按帧率 200fps（帧间隔 5ms）串行执行，一帧算不完就来了下一帧——你会丢帧，或者积压延迟越来越大。更根本的问题是：延迟链中的 `process_latency`（场景 3 建立的概念）会因此显著增大——因为"从图像到达到 Planner 发出指令"的时间窗被算力撑长了。

### 6.3 新的任务是什么

> **在有限算力的约束下，通过架构设计（而非单点算法优化）来控制系统延迟、提升吞吐量，使 `process_latency` 保持在可接受范围内，同时不牺牲算法精度。**

具体来说：
1. **缩短延迟**：让 `process_latency` 尽可能小（一帧从 catch 到 dispatch 的端到端时间）
2. **提高吞吐**：不丢帧，每一帧图像都被处理
3. **异步化指令下发**：控制指令以高于相机帧率的频率下发

### 6.4 怎么解决

> **本场景涉及的核心技术**：流水线并行 · 异步指令下发 · 推理吞吐量优化 · 传感器→探测→控制 三级解耦 · 高低频双线程架构

#### 6.4.1 降低延迟 vs 提高吞吐 — 两件不同的事

在讨论具体方案之前，先区分两个常被混淆的目标：

**降低延迟（Latency Reduction）**：让单帧从采图到出指令的时间更短。这是算法层面的优化——换更快的推理引擎、减少不必要的内存拷贝、用查表替代在线计算。延迟直接决定了延迟链中 `process_latency` 的大小——`total_delay` 中要往前预测的那个"已过去的时间"。

**提高吞吐（Throughput）**：让系统不丢帧。这是架构层面的优化——流水线化。**流水线不降低单帧延迟（甚至因同步开销而略微增大），但它让你在上一帧还在推理时就开始处理下一帧的采集和前处理，从而达到不丢帧的效果。** 延迟和吞吐是正交的目标——你可以有一个高延迟但高吞吐的系统（每帧慢但每帧都处理），也可以有一个低延迟但低吞吐的系统（每帧快但隔一帧丢一帧）。

本场景的目标是**同时追求两者**：通过流水线保证吞吐，通过算法精简控制延迟底线。

#### 6.4.2 流水线化：拆阶段，并行跑

回顾场景 3 中建立的完整处理链：

```
传感器采集 → 前处理 → 推理 → 角点精修 → PnP → EKF → Planner → 串口下发
```

在串行模式下，CPU/GPU 大部分时间在**等**——等推理结果时 CPU 闲着，等 CPU 做后处理时 GPU 闲着。**流水线化**的核心思想是：**把处理链拆成多个阶段，不同帧的不同阶段同时执行。**

流水线拆分遵循一个总原则：**把链中耗时最长、资源占用独立的阶段拆到单独线程。** 具体来说：

- 推理（YOLO-Pose）通常是最慢的，且独占 NPU/GPU，天然适合拆成独立线程
- 采集和 CPU 后处理（角点精修/PnP/EKF/Planner）共用 CPU，一般合在另一个线程
- 如果 CPU 后处理也特别重（如传统视觉角点精修很耗时），可以进一步拆成三线程：采集 / 推理 / 后处理

拆分后，系统吞吐由最慢的线程决定（通常是推理线程），单帧延迟 ≈ 推理耗时 + 线程同步开销（< 1ms）。不拆分时，吞吐 = 1/(所有阶段耗时之和)，拆得越多越接近 1/(最慢阶段耗时)。

> **参见 ALGORITHM_GUIDE.md §3.1** 中各 Stage 之间的数据包流转机制（pre2cap / cap2det / det2pre 通道设计）。

> **经验法则**：根据你的推理平台性能，150-300fps 的吞吐、10-15ms 的单帧延迟是各个平台上合理的（13400、8845hs、ax650、orin nx）。瓶颈在哪里就拆哪里——推理慢拆推理，后处理重拆后处理，两端都重就拆三段。

#### 6.4.3 异步化指令下发：检测用低频，控制用高频

流水线解决了"不丢帧"和"加速处理"的问题。但还有一个独立的优化方向：**控制指令的下发频率。**

从信息更新的角度，只有相机的新图像能带来敌方状态的新消息——所以**传感器→探测→状态更新的频率**受限于相机帧率（或推理瓶颈）。但从控制的角度，你可以**更高频地下发指令**——因为：

- EKF 在帧间也在做预测（匀速模型外推），状态估计在新图到来之前也在持续更新
- 按 500Hz 下发指令（而非 200Hz 的相机帧率），下位机的 PID 控制器得到更高频率的参考输入，跟踪的连续性和平滑度更好
- 对非线性运动模型的预测在上位机完成，提高下发频率能有效降低控制的离散化误差

**高低频双线程架构**（参考 sp25 开源）：

```
低频线程（~200Hz，与相机帧率同步）：
  传感器采集 → 前处理 → 推理 → 角点精修 → PnP → EKF 更新 → 刷新目标状态

高频线程（~500Hz，独立时钟）：
  从共享内存读最新目标状态 → EKF 预测（外推至"此刻"）→ Planner → 指令下发
```

两条线程通过加锁的共享变量交换数据——低频线程写入最新状态，高频线程读取并外推。这种架构将 `process_latency` 中的"Planner 等待"部分降到了几乎为零——因为 Planner 不再等着新图到来，而是在高频线程中随时取最新状态外推。

> **代码参考**：sp25 开源中的异步指令下发架构。

#### 6.4.4 延迟链收束：process_latency 的最终定义

经过场景 2（通讯延迟）、场景 3（采集延迟）和本场景（算力延迟），完整的 `process_latency` 被修正为：

```
process_latency = now() - data->time  （场景 3 的定义）
                = t_preprocess + t_inference + t_post + t_ekf + t_planner
                ≈ t_inference + t_pipeline_overhead

其中流水线化后，t_pipeline_overhead 是各阶段之间的同步开销（< 1ms）
       t_inference 通常是瓶颈
```

经过流水线化和异步化后，`total_delay` 链的实际预测窗口为：

```
total_delay = process_latency + send_latency + comm_latency + fly_time
                            ↑                         ↑
                    本场景压缩至此       (minimize by 500Hz dispatch)
```

> **参见 ALGORITHM_GUIDE.md §3.8.6** Planner 流程中的总延迟计算，以及 `planner/Planner.cpp#L371` 中 `total_delay = process_latency + comm_latency + fly_time` 的实现。

### 6.5 现在我们能做什么

**系统新增能力**：
- 通过流水线化，在不丢帧的前提下将吞吐量推到接近瓶颈阶段（通常是推理）的极限
- 通过异步化指令下发，以 500Hz 的高频向外输出控制指令，降低下位机控制的离散化误差
- `process_latency` 被压缩和可控——不再是串行的累加和，而是流水线中的阶段级延迟
- 延迟链中全四条（process / send / comm / fly_time）均已被定义或压缩

**仍存在的局限**：
- 你还是假设弹丸瞬间到达——`fly_time` 还没被算入真实预测（场景 7）
- 你还是只面对一个目标——多目标下的筛选、切换和双模型切换还未处理（场景 9）

3. 在流水线中故意插入人为延迟（模拟更慢的推理平台），观察延迟链是否在允许范围内

### 7.2 这次放松什么约束

- **放松约束 C2（发射机构物理约束）**：

1. **发射系统有散布**：弹丸不会精确沿枪管轴线飞出——每发弹的出口方向有微小随机偏差。距离越远，散布造成的弹着点偏差越大。

3. **弹丸有速度限制**：不再是无限弹速。弹丸从枪口飞到目标需要时间（`fly_time = distance / bullet_speed`），在此期间目标已经移动了一段距离。而且弹丸在飞行中受重力影响会下坠。

### 7.3 新的任务是什么

1. **弹道补偿**：将 `fly_time` 纳入 `total_delay`，前向预测 fly_time 后的目标位置，并在俯仰角上叠加重力补偿
2. **射击时序**：理解发弹延迟的物理本质——它不改变云台指向，只改变"何时下达开火指令"
3. **散布认知**：知道散布的量级，据此调整外参和射击距离预期

### 7.4 怎么解决

> **本场景涉及的核心技术**：弹丸飞行时间计算 · 弹道解算（解析/迭代） · 重力补偿 · 散布评估与量化 · 发弹延迟统计

#### 7.4.1 散布、射频、发弹延迟 — 物理世界的限制

**散布**

发射散布是机械和弹丸一致性的问题——找机械同学和电控同学解决。

> **经验法则**：小发射：5米一块小装甲大概60分水平，8米一块小装甲75分，12米一块小装甲90分。调好散布之后，记得跟着散布重新调一下相机外参。

**射频**

装甲板检测上限（20hz）决定你能多快响应目标。RM 一般实践给 20Hz 到 30Hz 的射击频率。

**发弹延迟**

找电控同学，打比如 300 发弹丸，统计从发出指令到摩擦轮掉速（弹丸发射）的时延。

> **经验法则**：100ms 时延、10ms 标准差算是比较好。如果不好，先让电控同学调。如果电控调不好，那可能是机械设计问题——单发限位力太大，或者链路阻力太大。

**发弹延迟的关键洞察**：发弹延迟不改变云台目标方向。想象你的弹丸像水流一样流向目标——上位机火控（指示下位机何时开火）就是控制水流的开关。当发弹延迟变化时，你并不需要改变云台的指向，你只需要**改变下发开火指令的时机**。`single_shoot_latency` 作为一个前向偏移量，在 Planner 中用于决定"提前多少毫秒发出 fire 指令"，而非在瞄准角度计算中参与。

> **参见 ALGORITHM_GUIDE.md §3.8.4** 射击决策逻辑，以及 `planner/Planner.cpp` 中 `single_shoot_latency` 与 `continue_shoot_latency` 的使用。

#### 7.4.2 弹丸飞行时间计算：fly_time 进入延迟链

场景 2 建立的延迟链中，`fly_time` 一直是"待填补"的。现在补上：

```
total_delay = process_latency + comm_latency + fly_time
                                              ↑
                                        本场景补上
```

**fly_time 的基本计算**：

最简单的情况——忽略空气阻力，弹丸做抛物线运动：

```
给定目标水平距离 d 和高度差 h，弹丸初速度 v₀：

飞行时间 t 满足：
  a·t² + b·t + c = 0

其中 a = g·d²/(2·v₀²), b = -d, c = a + h

取较小正根 → fly_time
```

对于小弹丸（17mm, 3.1g, 25m/s），无空气阻力的解析模型通常就足够了。

对于大弹丸（42mm, 45g, 16m/s），飞行时间更长且弹丸质量/截面积比不同，理论上需要考虑空气阻力——一般取球体的典型 `Cd = 0.5`，使用**迭代法**（牛顿法）求解发射角和飞行时间。代码中 `cal_fly_time` 函数在 `consider_air_resistence=true` 时，通过反复调整发射角 θ 使计算出的高度误差收敛到零，从而得到补偿空气阻力后的飞行时间。**注意**：笔者没有验证过长距离下大弹丸的空气阻力补偿效果是否显著。

> **代码参考**：`mathutils/math_tools.hpp` 中的 `cal_fly_time()` 函数，包含不考虑/考虑空气阻力两种模式。在 Planner 中每次计算瞄准点时调用，传入 `consider_air_resistence` 标志（由配置文件控制）。

**fly_time 的循环依赖与处理**：

你可能会注意到一个鸡生蛋问题——`fly_time = f(target_pos)`，而 Planner 需要 `fly_time` 来确定 `total_delay`，再用 `total_delay` 来预测未来位置。实际上在代码中，第一次 `cal_fly_time` 用的是当前目标位置（未外推），得到一个初始的 `fly_time` 和 `total_delay`，然后用这个 `total_delay` 外推目标位置。2026 年的主流实践是采取 2 次或 3 次迭代（每次用外推后的新位置重算 fly_time，直到收敛），但不迭代、仅用一次近似的效果也可以接受。

#### 7.4.3 弹丸重力下落补偿

弹丸在空中飞行时，重力让它持续下坠。下坠量约为：

```
Δz = 0.5 × g × fly_time²
```

补偿方式：在计算云台目标俯仰角时，从目标的世界坐标 Z 中扣除这个下坠量：

```cpp
// 参见 Planner.cpp cal_gimbal_target 函数
pw(2, 0) -= 0.5 * g * fly_time * fly_time;  // 重力下降补偿
// 然后再从世界坐标转换到云台角度
```

这意味着 Planner 瞄准的是"弹丸落点"而非"目标当前高度"。`fly_time` 越大（目标越远），下坠越明显，俯仰角补偿越大。如果启用了空气阻力补偿（大弹丸），此处的 `fly_time` 已经是 §7.4.2 中迭代求解的补偿后值——重力下坠公式本身不需要再单独考虑空阻修正。

> **参见 ALGORITHM_GUIDE.md §3.8.2** 弹道补偿与飞行时间计算，以及 §3.8.6 Planner 完整流程中 `cal_gimbal_target` 的重力补偿步骤。

- 你还是只面对一个目标——多目标下的筛选、切换和双模型切换还未处理（场景 9）

- C1：单目标

### 8.2 这次放松什么约束

- **进一步放松约束 C2（云台动力学）**：云台响应指令需要时间——不再能瞬间摆动到任意角度。

具体来说，云台作为一个物理系统有两个关键限制：

1. **运动学限制**：云台有最大角速度和最大角加速度。以典型 RoboMaster 云台为例——yaw 轴最大角加速度约 50 rad/s²，pitch 轴约 100 rad/s²。这意味着你说"下一秒转到 30°"时，云台需要先加速、再匀速、再减速——它不可能跳变。

2. **动力学干扰**：云台在转动时受到库伦摩擦（恒定阻力，与速度方向相反）、粘滞阻尼（与速度成正比的阻力）和转动惯量（阻止角加速度的惯性力）的共同作用。PID 控制器需要在有这些干扰的情况下完成轨迹跟踪。

如果不管这些限制，直接把 Planner 算出的目标角度当阶跃指令下发，会发生什么？云台会以最大加速度冲过去，然后超调、震荡、再收敛——期间弹着点严重偏离目标。

### 8.3 新的任务是什么

> **在云台有物理动力学约束的前提下，让 Planner 输出一条云台物理上可执行的平滑轨迹，使下位机能以最小的跟踪误差跟随目标——同时保持射击精度。**

具体来说：
1. **MPC 轨迹优化**：在 Planner 中嵌入云台的物理约束（max_yaw_acc / max_pitch_acc），生成平滑的角度和角速度曲线，而非阶跃指令
2. **三阶指令下发**：向云台下发的不仅是目标角度，还有目标角速度和角加速度——让下位机做速度前馈和加速度前馈，大幅降低跟踪误差
3. **跨组协作流程**：建立视觉组 → 机械组 → 电控组的性能需求传递和验收链路

### 8.4 怎么解决

> **本场景涉及的核心技术**：云台运动学建模 · 速度前馈 PID · 动力学前馈（库伦摩擦/粘滞阻尼/转动惯量） · MPC 轨迹优化（TinyMPC/ADMM） · 位置-速度-加速度三阶指令下发 · 跨组协作验收流程

#### 8.4.1 从需求到验收：让机械和电控交付一个好云台

自瞄的上限不仅由视觉算法决定——云台的跟踪能力是硬天花板。以下是视觉组推动机械和电控同学交付一个合格云台的完整协作流程：

**Step 1: 定义工况 — 视觉给出需求**

选取一个有代表性的跟踪场景：3m 距离、0.3m 半径、3 号全向轮步兵，60rpm，始终打最靠近你的那块装甲板。根据这个场景和下文 §8.4.2 所述 MPC 生成的目标轨迹，可以提取出一组目标跟踪曲线：yaw 角和 pitch 角随时间的变化。

**Step 2: 提取参数 — 从曲线到性能指标**

从上述曲线中提取关键参数：摆动的幅度（±多少度）、频率（Hz）、最大角速度和最大角加速度。在刚才的场景里，yaw的摆幅是左右各4°，4hz。这也是笔者常用的基准测试正弦波的参数。这些数据交付给机械同学。

**Step 3: 机械设计 — 画出包线图**

机械同学在 SolidWorks 中量好云台的转动惯量和最大重力矩（一般只有 pitch 轴有），配合所选电机的参数（力矩、转速），对每个轴画出简易包线图：在给定电压/电流下，能达到的最大角加速度和最大角速度是多少？包线图必须覆盖视觉需求的工况点——如果不能，需要换电机或减重。

作为参考，这里列举出几个典型云台的转动惯量：

上交25串联腿步兵开源下供弹云台：约12000kg·mm2
上交23五连杆平衡步兵开源中供弹云台：空载约40000kgmm2，满载约60000kgmm2
哈工大24半舵半全底盘大小yaw云台的大yaw：空载约80000kgmm2，满载约110000kgmm2

对于 1.2Nm 持续扭矩的 GM6020 电机，它们的理论角加速度是（`α = τ / I`，已换算为 rad/s²）：

| 云台 | 转动惯量 | 理论角加速度 |
|------|---------|------------|
| 上交25串联腿步兵下供弹 | 12000 kg·mm² | **100 rad/s²** |
| 上交23五连杆平衡步兵中供弹（空载） | 40000 kg·mm² | **30 rad/s²** |
| 上交23五连杆平衡步兵中供弹（满载） | 60000 kg·mm² | **20 rad/s²** |
| 哈工大24大小yaw大轴（空载） | 80000 kg·mm² | **15 rad/s²** |
| 哈工大24大小yaw大轴（满载） | 110000 kg·mm² | **11 rad/s²** |

可以看到，云台惯量越大，理论角加速度越小——上交的轻量化下供弹云台能跑到 100 rad/s²，而哈工大的双轴大 yaw 满载时仅 11 rad/s²。这就是为什么达妙4310（大扭矩）或者双级yaw（自瞄云台轻量化）被追捧的原因：视觉从来都不会觉得云台角加速度太大。

**Step 4: 电控调试 — 跟踪仿真曲线**

电控同学拿到机械交付的云台后，用视觉组提供的仿真自瞄曲线做跟踪测试。一般从正弦跟踪开始（频率和幅度对应 Step 2 的提取值），再过渡到实际自瞄工况曲线。多测几个不同转速和距离的工况。

**Step 5: 分析跟踪误差 — 回到射击命中率**

将跟踪曲线的角度误差映射回视觉场景中的角度差。已知散布的概率分布或大致散布圆，可以根据瞄准点偏差估算"云台跟踪误差导致的命中率下降量"。如果命中率在散布裕度内，调试通过；如果误差太大——找电控同学继续调。

这一步建立了闭环：**视觉定义需求 → 机械保证能力 → 电控实现跟踪 → 视觉回归验收**。

#### 8.4.2 MPC 轨迹优化：给云台一条"它能追上的曲线"

场景 7 的 Planner 已经计算出了"目标在未来每一帧的位置"。但如果你把这些位置逐帧转成角度直接下发，得到的是一条**锯齿状折线**——因为 PnP 的观测噪声会逐帧抖动，直接下发等于让云台追着噪声跑。

MPC 的作用是在知道目标未来轨迹的前提下，**求解一条满足云台物理约束的最优平滑轨迹**。同济大学2025年视觉开源的总readme对此做出了相当详细的解释，推荐阅读。

以偏航轴为例（参见 ALGORITHM_GUIDE §3.8.3）：

```
给定 HORIZON=100 步的参考轨迹 yaw_ref (基于 EKF 整车模型预测)
云台约束: |acc_k| ≤ max_yaw_acc = 50 rad/s²

求解:
  minimize Σ[(yaw_k - yaw_ref_k)² + w_vel × (vyaw_k - vyaw_ref_k)²]
  s.t.  yaw_{k+1} = yaw_k + vyaw_k × DT
        vyaw_{k+1} = vyaw_k + acc_k × DT
        |acc_k| ≤ 50
```

物理直觉：MPC 不是在"瞄准"，而是在"规划"。它以当前时刻为中心，向前后各看约 0.5 秒（共 100 步 × 0.01s = 1.0s 窗口，HALF_HORIZON = 50 步），然后问自己："以我的最大加速度 50 rad/s²，我能在每一帧都尽可能靠近目标吗？"

为什么必须前后都看？因为目标在高速自转时，装甲板会周期性切换——你瞄准的板子可能在 0.3 秒后转到背面，你需要提前知道"我要在什么时候减速、什么时候反向加速去追下一块板"。如果只看未来、不看过去，每次 EKF 更新状态后 MPC 重新规划出的轨迹会不连续——在装甲板切换的瞬间出现跳变。前后各看 0.5 秒让 MPC 能看到完整的"当前这块板从出现到消失"的窗口，从而给出平滑的跨装甲板切换轨迹。

本系统使用 **TinyMPC（ADMM 求解器）** 在线求解。ADMM 的优势在于每次迭代的计算量极小且固定——适合实时嵌入式场景。偏航轴和俯仰轴各维护一个独立的 2 维 MPC 求解器（状态：[角度, 角速度]），每帧求解后取 HALF_HORIZON（50 步 = 0.5s）处的优化值作为下发的指令。

> **参见 ALGORITHM_GUIDE.md §3.8.3** MPC 问题形式化和 §3.8.6 Planner 完整流程中 MPC 求解步骤。代码实现见 `planner/Planner.cpp` 中的 `setup_yaw_solver/setup_pitch_solver` 和 `get_trajectory`。

#### 8.4.3 三阶指令下发与下位机控制系统设计

在场景 1-7 中，Planner 下发的只有目标角度。有了 MPC 轨迹后，你同时知道了目标角速度和目标角加速度——上位机可以把完整的"期望运动轨迹"交给下位机，让下位机能用**物理模型**做前馈，而不仅是"追着一个目标角度跑"。

**协议接口：视觉 → 电控**

```
每 2ms（500Hz）下发一帧:
  yaw_angle, yaw_speed, yaw_acc       → yaw 轴的 (位置, 速度, 加速度) 目标
  pitch_angle, pitch_speed, pitch_acc  → pitch 轴同理
```

视觉不需要关心下位机内部怎么实现控制。但你需要理解物理上发生了什么，才能看懂电控的调试结果，并在跟踪效果不好时判断"是视觉轨迹给得不好还是电控没跟上"。

**单轴云台动力学模型**

云台的一个轴（yaw 或 pitch）可以用以下物理方程描述：

```
J · α + B · ω + C · sign(ω) + G(θ) = τ_motor = K_t · I

其中:
  J        — 转动惯量 (kg·m²)
  B        — 粘滞阻尼系数 (Nm/(rad/s))
  C        — 库伦摩擦幅值 (Nm)
  G(θ)     — 重力矩 (Nm)，仅 pitch 轴非零 (G = mgr·sin(θ))
  τ_motor  — 电机输出扭矩 (Nm)
  K_t      — 电机扭矩常数 (Nm/A)
  I        — 电机电流 (A)
  α / ω / θ — 角加速度 / 角速度 / 角度
```

等号左边四项是"物理世界阻止电机转动的力"，等号右边是"电机必须输出的力"。控制的目标是用电流 `I` 精确驱动 `θ` 沿目标轨迹运动。

**前馈：用物理模型预测所需的力**

MPC 给出了目标轨迹 `(θ_target, ω_target, α_target)`。如果物理参数已知，你可以**直接算出**沿这条轨迹运动所需的电流：

```
τ_ff_inertia  = J · α_target              // 克服转动惯量：要加速就要出力
τ_ff_viscous  = B · ω_target              // 克服粘滞阻尼：转得越快阻力越大
τ_ff_coulomb  = C · sign(ω_target)        // 克服库伦摩擦：恒定阻力，方向随速度翻转
τ_ff_gravity  = mgr · sin(θ_target)       // 克服重力矩（仅 pitch）：角度越大重力拉力越大

总前馈扭矩: τ_ff = τ_ff_inertia + τ_ff_viscous + τ_ff_coulomb + τ_ff_gravity
前馈电流:   I_ff = τ_ff / K_t
```

四项前馈各自补偿不同的物理效应。参数 `J, B, C, mgr, K_t` 由电控同学通过系统辨识获得（见下方协作清单）。

注：上科大26视觉方案里舍弃了库伦摩擦，这是因为和几个队伍交流之后发现它的阶跃属性会让控制不稳定，即使增加了近0平缓也还是难以缓解。

**反馈：修正模型不准和外界扰动**

前馈再准，参数辨识也有误差，外界也可能有扰动。PID 反馈负责修正残余误差：

```
e_pos = θ_target - θ_current     // 位置误差
e_vel = ω_target - ω_current     // 速度误差

τ_fb = Kp · e_pos + Kd · e_vel + Ki · ∫ e_pos dt
I_fb = τ_fb / K_t
```

**完整控制架构**

```
MPC 轨迹:  θ_target(t), ω_target(t), α_target(t)
  │
  ├── 前馈路径（物理模型，开环）:
  │   I_ff = (J·α_target + B·ω_target + C·sign(ω_target) + G(θ_target)) / K_t
  │
  ├── 反馈路径（PID，闭环）:
  │   I_fb = (Kp·e_pos + Kd·e_vel + Ki·∫e_pos) / K_t
  │
  └── 总电流指令:
      I_cmd = I_ff + I_fb  →  电流环（FOC / 电机驱动）  →  电机出力
```

前馈提供了 80-90% 的驱动力（因为物理模型覆盖了主要的动力学效应），PID 只负责修正剩下 10-20% 的误差。对比纯 PID 反馈——需要先产生误差才能纠正——前馈 + 反馈架构的跟踪延迟和超调量都大幅降低。

这种"位置-速度-加速度/电流"三级控制中，电流是最内层——它直接正比于扭矩，是云台最底层的物理控制量。PID 输出的 `I_fb` 直接叠加在前馈电流上，控制回路因此只有一层（电流/扭矩层），避免了外环 PID→内环 PID 的级联延迟。

**视觉和电控的调试协作清单**：

| 事项 | 视觉负责 | 电控负责 |
|------|---------|---------|
| 协议格式 | 定义指令结构（三阶数据），写进文档 | 按协议解析 |
| 指令频率 | 告知下发频率（如 500Hz） | 确认串口接收缓冲区不溢出；在两帧指令间做线性插值 |
| 系统辨识 | — | 辨识 `J, B, C, mgr, K_t`（通过阶跃响应/正弦扫频/离线测量） |
| 前馈实现 | — | 在控制循环中按物理模型计算四项前馈并叠加 |
| PID 调参 | — | 在前馈到位后，对残差做 PID 闭环修正 |
| 跟踪效果反馈 | 收到跟踪误差曲线，判断是否影响命中率 | 提供跟踪误差曲线（位置误差 vs 时间）|

> **参考**：sp25 开源的"轨迹视角下的自瞄理论"——将自瞄决策从"逐帧计算瞄准点"升级为"规划一条云台可执行的最优轨迹"。在 2m 距离、14rad/s 转速下击杀时间仅 10s（来自 sp25 readme 国赛数据）。

#### 8.4.4 整个指令链的完整视图

经过所有场景的累积，你的指令链最终形态如下：

```
Planner (上位机, 500Hz)
  │
  ├── EKF 状态 → 预测未来 HORIZON 步的目标位置
  │
  ├── get_trajectory → 生成参考轨迹(位置+速度)
  │
  ├── TinyMPC 求解 → 满足物理约束的最优轨迹
  │   max_yaw_acc=50 rad/s² / max_pitch_acc=100 rad/s²
  │
  └── 提取 HALF_HORIZON 处优化值：
      target_yaw / target_yaw_speed / target_yaw_acc
      target_pitch / target_pitch_speed / target_pitch_acc
      + fire_enable / target_distance / target_id
      → 串口下发

下位机 (单片机, ~1kHz)
  │
  ├── 指令插值 + 目标轨迹重建
  │
  ├── 前馈路径（物理模型）:
  │   I_ff = (J·α + B·ω + C·sign(ω) + G(θ)) / K_t
  │
  ├── 反馈路径（PID）:
  │   I_fb = (Kp·e_pos + Kd·e_vel + Ki·∫e_pos) / K_t
  │
  ├── I_cmd = I_ff + I_fb → 电流环（FOC）→ 电机驱动
  │
  └── 射击机构控制（开火 + 拨弹）
```

> **参见 ALGORITHM_GUIDE.md §3.8.5** RobotCommand 数据结构定义，§3.8.4 射击决策逻辑。

## 场景9
### 9.1 我们从哪里来

在场景 8 结束时，你的自瞄系统拥有了完整的单目标全链路：
- 感知（探测→角点精修→PnP降自由度）→ EKF 整车跟踪 → 弹道补偿 → MPC 轨迹优化 → 三阶指令下发
- 延迟链 `total_delay` 全四项就位，云台指令带有物理前馈

但所有这些能力都建立在一个最后的假设上：**C1——视野里只有一个目标。** 从场景 1 到场景 8，你一直假设屏幕上只有那台 3 号全向轮步兵。在真实赛场上，8 台敌方机器人同时在场——不同编号、不同颜色、不同装甲板尺寸、不同兵种、不同距离、不同运动状态。

C1 是最后一道被放松的约束。**所有约束至此全部解除。**

### 9.2 这次放松什么约束

- **放松约束 C1（多目标场景）**：赛场上有许多目标——不同编号、颜色、装甲板尺寸、兵种。

YOLO 在一帧中可能输出 3-5 个检测框。你需要决定：**打哪一个？当前正在跟踪的目标还在吗？如果出现了一个更高价值的目标，要不要切换？** 具体来说：

1. **多检测框 → 选谁打**：一个近距离的 4 号步兵和一个远距离的哨兵同时出现——你需要一套打分机制而不是简单取最近
2. **目标暂时丢失 → 要不要继续相信**：目标可能被障碍物短暂遮挡，也可能转到了视角背面——你需要区分"短暂丢失"和"彻底丢失"
3. **装甲板切换 → 是不是同一辆车**：目标自转时，上一帧看到的是装甲板 A，这一帧变成了装甲板 B——你需要识别这是"同一辆车换了一块板"而非"换了一辆车"
4. **高价值目标出现 → 要不要切换**：正在打 3 号步兵时，敌方英雄残血出现在视野中——你需要切换优先级逻辑

### 9.3 新的任务是什么

> **在多目标赛场环境中：正确筛选目标、管理多跟踪器、检测装甲板切换、识别目标身份和兵种——最终选出最优打击目标并稳定跟踪。**

具体来说：
1. **目标筛选与优先级**：给每个检测框打分，选出最高价值目标
2. **多跟踪器管理**：每个潜在目标维护独立的 EKF 跟踪器，当最优目标丢失时可快速回退到次优目标
3. **装甲板切换检测**：识别同一辆车上的装甲板轮换，避免误判为"目标丢失"或"换了目标"
4. **双模型自适应融合**：基于目标转速在装甲板模型和整车模型之间自动切换

### 9.4 怎么解决

> **本场景涉及的核心技术**：加权打分筛选（距离+中心度） · 多跟踪器管理 · 跟踪状态机（IDLE→DETECTING→TRACKING→TEMP_LOST） · 装甲板切换检测（马氏距离匹配 + ab_counter） · 双模型自适应切换 · 颜色分类与目标识别 · 大小装甲板自动区分

#### 9.4.1 目标筛选：两种策略——自动打分 vs 指点锁定

在多目标场景中，**"选谁打"是核心决策**。社区有两种主流方案，它们互为替代：

| 方案 | 核心思路 | 适用场景 |
|------|---------|---------|
| **自动打分**（§9.4.1A） | 系统根据距离+中心度+兵种优先级自动计算每个目标的分数，选最高分 | 操作手不想管瞄准，完全交给算法；哨兵或全自动兵种 |
| **指点锁定**（§9.4.1B） | 操作手手动将目标置于画面中央 → 系统锁定该目标 → 开火权激活后始终跟踪此目标 | 步兵/英雄等需要操作手主动选择目标；高质量人机协作 |

两者的**跟踪状态机、装甲板切换检测、双模型融合**完全相同——区别仅在于"最初选谁以及切换目标的触发条件"。你只需选择一种，不需要同时实现两者。

##### 9.4.1A 策略 A：自动打分机制

每一帧 YOLO 可能输出多个装甲板。你不能简单取最近的——一个 1m 处背对你的 5 号步兵未必比一个 3m 处正对你的 3 号步兵更好打。你需要一个综合打分：

```
Score = w_dist × Distance_Score  +  (1 - w_dist) × Center_Score

Distance_Score = 1.0 - distance / max_distance_accept     (0~1, 越近越高)
Center_Score   = 1.0 - pixel_dist / maxSD                 (0~1, 越靠近图像中心越高)

w_dist = 0.6    （距离权重，优先选近处的目标）
```

**为什么需要 Center_Score？** 原因很简单：图像中央的装甲板通常正对你（偏航角小），PnP 解算精度最高、角点在遮挡最小的位置、弹道也最直接。一个在画面边缘的装甲板（即使距离近）可能是大角度侧对你——五个角点可能被遮住两个。

**筛选的前置硬条件**（任何一项不满足就直接丢弃）：
- 颜色必须匹配敌方颜色（`enemy_color`）
- 偏航角 `|yaw| < max_yaw_accept`（0.85 rad ≈ 48.7°，视野范围内）
- 距离 `< max_distance_accept`（4.5 m）
- 高度 `< max_height_accept`（1.5 m）

> **参见 ALGORITHM_GUIDE.md §3.7.1** 装甲板筛选的完整打分公式和参数。

**实战补充（sp25 的做法）**：

除了打分，sp25 还引入了一层**优先级排序**：对不同兵种赋予不同优先级（如英雄 > 步兵 > 哨兵），在加权打分后按优先级做二次排序。当正在跟踪的目标状态稳定且出现了更高优先级的目标（如敌方英雄残血出现），触发目标切换——以新目标重新初始化跟踪器。切换不是即时的——需要状态机先进入 `switching` 态，确认新目标存在后才进入 `detecting`，防止因为一帧的误检就频繁切换。

**已跟踪目标的特殊处理**：已在跟踪中的目标不会进入"新目标"候选池重新打分——它们直接进入各自对应跟踪器的 `update_target` 路径。只有空闲的跟踪器（`IDLE` 态）才会从候选池中选最高分的新目标来初始化。

##### 9.4.1B 策略 B：指点锁定机制

自动打分在大多数情况下有效，但它有一个盲区：**算法不知道你想打谁。** 两个步兵同时出现在 3m 处——算法会随机选一个（打分相近），但操作手可能看到左边那个残血、或者右边那个正在威胁队友。这是人的战术判断，算法永远无法替代。这也是上海科技大学2026年自瞄的主力锁定逻辑。

指点锁定把"选目标"还给操作手，系统只负责"锁定后不丢"：

```
操作手未给自瞄开火权（手动档/指点点）:
  系统不跟踪任何特定目标
  但在每一帧中，始终计算并输出"当前画面最中心的敌车是谁"
  目的：让操作手能看到"如果你现在给自瞄权，系统会锁定谁"

操作手给自瞄开火权（自瞄档）:
  系统检查：当前画面中央是否有敌车？
    ├── 有 → 锁定这辆车（以该车的 tag_id + 颜色初始化跟踪器）
    │        进入 DETECTING → TRACKING 状态机
    │        锁定后不再自动切换目标（即使出现更高分的目标也不切）
    │        → 除非该目标完全丢失（回到 IDLE），否则始终跟踪它
    │
    └── 无 → 保持 IDLE，等待操作手将云台对准目标
```

**与自动打分的核心区别**：

| 维度 | 自动打分 | 指点锁定 |
|------|---------|---------|
| 初始目标选择 | 系统自动计算分数 | 操作手瞄准 → 系统抓取画面中央的目标 |
| 跟踪期间切换 | 更高分目标出现时可能自动切换 | **锁定后不自动切换**——除非当前目标完全丢失 |
| 操作手负担 | 低——算法全自动 | 中——需要主动选目标，但锁定后解放双手 |
| 实现复杂度 | 需要完善的打分函数和优先级逻辑 | 需要判断"画面中央"和接收下位机开火权信号 |

**实现要点**：

1. **判断"画面最中心"**：不是取所有检测框中 `pixel_dist` 最小的——而是取 `pixel_dist < R_center`（中心半径阈值，如画面宽度的 20%）的检测框中 tag_id 持续稳定的那个。如果中心区有多个框，取最近的那个。
2. **锁定条件**：操作手给定自瞄信号（下位机串口 → `RobotStatus.program_mode == AUTO_AIM`） + 画面中心区存在有效检测框 + 连续 4 帧确认（复用 DETECTING 逻辑）
3. **解锁条件**：操作手切回手动档，或者目标丢失超过 30 帧（TEMP_LOST 超时回到 IDLE）
4. **锁定期间的唯一性**：锁定后，该跟踪器的目标不再参与新目标打分池。即使画面边缘出现了更高价值的敌车，不切换——操作手手动切回手动档再重新给自瞄权，才会重新锁定。

**为什么选指点锁定？** 因为比赛中操作手天然会"把云台大致指向他想打的方向"——这不是额外的操作，而是他已经在做的事。指点锁定只是把他已经在做的"指"变成了系统的"就这样，锁定"。相比全自动打分——算法可能在操作手不想换目标时突然切换（因为另一台车跑近了），破坏操作手感。

#### 9.4.2 跟踪状态机：IDLE → DETECTING → TRACKING → TEMP_LOST

单目标时，场景 5 的 EKF 不需要状态机——有观测就更新，没观测就外推。多目标时必须有状态机来决定"这个跟踪器对应的目标还在不在、要不要释放给其他目标用"。经典的四态状态机：

```
        ┌──────────┐
        │   IDLE   │◄──── 连续丢失超过阈值 (30帧) ────┐
        └────┬─────┘                                   │
             │ 发现新目标，初始化跟踪器                   │
             ▼                                          │
        ┌──────────┐                                   │
        │DETECTING │ (连续 4 帧检测成功后进入 TRACKING)   │
        └────┬─────┘                                   │
             │ 稳定检测                                  │
             ▼                                          │
        ┌──────────┐      短暂丢失（1帧）      ┌───────────┐
        │ TRACKING │◄────────────────────────►│ TEMP_LOST │
        └──────────┘    重新匹配恢复           └─────┬─────┘
                                                    │
                                                    └── 持续丢失 > 30帧 → IDLE
```

**各状态的物理含义**：

| 状态 | 含义 | 跟踪器行为 | 转换条件 |
|------|------|----------|---------|
| `IDLE` | 空闲——跟踪器未被分配 | 从候选池选最高分新目标 | 新目标出现 |
| `DETECTING` | 检测中——发现疑似目标，但还不确定 | 连续计数，暂不对外输出 | 连续 4 帧有观测 → TRACKING；中断 → IDLE |
| `TRACKING` | 稳定跟踪 | EKF 正常预测+更新 | 丢失 1 帧 → TEMP_LOST |
| `TEMP_LOST` | 暂时丢失——可能是短暂遮挡 | EKF 仅预测（靠外推维持），等待重新匹配 | 恢复匹配 → TRACKING；超 30 帧 → IDLE |

**`DETECTING` 状态的必要性**：防止 YOLO 的偶发误检导致跟踪器被"假目标"占据。连续 4 帧确认后才进入 `TRACKING`——这 4 帧约 20ms 的延迟换来了跟踪器的稳定性。

**`TEMP_LOST` 状态的必要性**：目标可能被障碍物短暂遮挡（0.1-0.3s），此时 EKF 应继续外推而不是立即判定丢失。30 帧的超时阈值约 150ms——足够大多数短暂遮挡恢复，又不会让跟随"幽灵目标"的跟踪器浪费太久。

> **参见 ALGORITHM_GUIDE.md §3.7.3** 跟踪器状态机的完整定义和状态转换条件。

#### 9.4.3 装甲板切换检测：是同一辆车换了块板，还是换了辆车？

高速旋转的目标上，装甲板在周期性切换——上一帧你看到装甲板 A，下一帧它转过去了，装甲板 B 进入视野。你的 EKF 整车模型（场景 5）本身跟踪的是"车辆"——旋转中心和转速——所以它能自然地处理装甲板切换。但问题是：**当新的一帧观测到来时，你怎么知道它对应的是同一辆车（只是换了块板），还是另一辆车？**

答案是**马氏距离匹配（已在场景 5 §5B.4 建立）** + **位置变化检测**：

```
对于每一帧的观测 z_meas 和每个跟踪器的预测 z_pred：
  d² = (z_meas - z_pred)^T × S⁻¹ × (z_meas - z_pred)

如果 d² < χ²(4) 的 95% 阈值 → 同一辆车（无论当前是哪块装甲板）
如果 d² ≥ 阈值 → 可能是另一辆车，或者是噪声异常

同时检查位置变化：
  ||new_pos - tracked_pos|| < same_position_threshold (0.2m)
  → 如果超过阈值 → 装甲板切换（同一辆车换了块板）
  → 如果没超过 → 正常跟踪
```

**装甲板切换后的处理**：
- 装甲板模型 KF 需要用新位置的观测重置（因为装甲板跳到了车辆的另一端，匀速假设被打破）
- 但 EKF 整车模型**不需要重置**——它跟踪的是车辆，不是单块装甲板。EKF 通过观测函数 `h_armor_xyz(x, id)` 自动在 4 块装甲板（id=0,1,2,3）之间切换投影
- `ab_counter` 在 0/1 之间切换，标识当前跟踪的具体装甲板对（四块板分为两对，每次可见一对）

> **参见 ALGORITHM_GUIDE.md §3.7.3** 装甲板切换检测（`same_position_threshold = 0.2m`、`ab_counter`）和整车模型可信度判断。

#### 9.4.4 双模型自适应融合：根据转速切换跟踪策略

场景 1 和场景 5 已经建立了两种模型的概念。在多目标场景下，**每个跟踪器内部都同时维护双模型**——根据目标的实时转速在主模型之间自动切换：

| 转速区间 | 活跃模型 | 说明 |
|---------|---------|------|
| `|vyaw| < 0.7 rad/s` | **装甲板模型**（4×1D KF） | 目标基本不转，跟踪装甲板的平移即可 |
| `0.7 ≤ |vyaw| ≤ 2.7 rad/s` | **双模型融合**（BOTH） | 过渡区：两个模型同时运行，按装甲板位置变化幅度加权 |
| `|vyaw| > 2.7 rad/s` | **整车模型**（11D EKF） | 目标高速自转，必须用整车 EKF 跟踪旋转中心+转速 |

切换逻辑带滞回——从装甲板模型升到 BOTH 的阈值是 0.7，但从 BOTH 降回装甲板模型的阈值也是 0.7（而非更低），防止在阈值附近来回震荡。同理，BOTH↔整车模型的切换阈值也是对称的 2.7 rad/s。

**整车模型可信度判断**：整车 EKF 需要"看到旋转"才能收敛它的旋转参数（`r`, `vyaw`, `dz`）。`rotate_counter` 统计观测到的转速超过阈值的连续帧数——至少 3 次以上才认为模型可信。如果转速估算突然发散（`|vyaw| > 3 rad/s` 持续 30 帧），整车 EKF 被重置并降回装甲板模型。

> **参见 ALGORITHM_GUIDE.md §3.7.3** 双模型跟踪架构和 §5.3 关键阈值汇总。

#### 9.4.5 颜色分类、目标识别与大小装甲板区分

**颜色判断**：敌方颜色（红/蓝）由裁判系统串口下发（`RobotStatus.enemy_color`）。检测到的装甲板颜色通过灯条区域的 `sum(R) vs sum(B)` 判断（场景 5 §5A.2）。颜色不匹配的检测框直接丢弃——你不会去打队友。

**目标标号（tag_id）**：YOLO 输出的 `tag_id` 标识了兵种编号：`1=英雄, 2=工程, 3/4/5=步兵, 6=哨兵, 7=前哨站, 8=基地`。这个标号有两个用途：
1. 跟踪器绑定：同一 `tag_id` 的检测框优先匹配到对应的跟踪器
2. 大小装甲板判断：`tag_id` 结合检测框长宽比 → 自动判断当前检测到的是大装甲板（英雄）还是小装甲板（步兵/哨兵），选用对应的 3D 模型点做 PnP

> **参见 ALGORITHM_GUIDE.md §3.7.2** 装甲板 3D 模型点（大装甲板 22.8cm vs 小装甲板 13.5cm）。

#### 9.4.6 完整的多目标跟踪流程

```
YOLO 输出: bboxes[] (3~5 个检测框)

  │
  ├── [预筛选] 颜色匹配 → 距离 < 4.5m → yaw < 48.7° → 高度 < 1.5m
  │   不满足任一条件 → 丢弃
  │
  ├── [分类] 已跟踪目标 → armors_in_tracking[]
  │         新目标 → new_armors[]
  │
  ├── [目标选择] 二选一:
  │   ┌── 策略 A（自动打分）: new_armors 按 Score 排序
  │   │
  │   └── 策略 B（指点锁定）:
  │       操作手已给开火权？
  │         ├── 否 → 始终输出"画面最中心的敌车"（提示操作手），保持 IDLE
  │         └── 是 → 画面中心区有有效检测框？
  │                  ├── 有 → 锁定该框，初始化跟踪器 → DETECTING
  │                  └── 无 → 保持 IDLE，等操作手瞄准
  │
  ├── [跟踪器状态机]（两种策略共用）
  │   ├── IDLE 跟踪器 → 从 new_armors[0]（策略A）或 锁定框（策略B）初始化
  │   ├── DETECTING → 连续 4 帧有匹配 → TRACKING
  │   ├── TRACKING → 马氏距离匹配 + 位置变化检测
  │   │   ├── 匹配成功 + 位置跳变 < 0.2m → EKF 更新
  │   │   ├── 匹配成功 + 位置跳变 > 0.2m → 装甲板切换，重置装甲板 KF，保持 EKF
  │   │   └── 匹配失败 → TEMP_LOST（EKF 仅预测）
  │   ├── TEMP_LOST → 30 帧内恢复 → TRACKING；超时 → IDLE
  │   └── 策略 B 特别：TRACKING 期间不自动切换目标
  │
  └── [模型自适应] 基于转速 |vyaw| 选择装甲板 / BOTH / 整车模型
      整车模型需 rotate_counter ≥ 3 才标为可信
```
